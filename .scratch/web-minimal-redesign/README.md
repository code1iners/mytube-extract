# Web 최소 구성 재설계 — 구현 티켓

사용자가 승인한 8개 분해안과 선행 관계를 개별 티켓으로 발행했다. 모든 티켓의 초기 상태는 `ready-for-agent`다. 이번 승인은 티켓 발행까지이며, 제품 구현은 사용자의 별도 구현 요청 후 시작한다.

선행 티켓이 없는 시작점은 **01·04**다. 선행 티켓이 모두 완료된 티켓을 이어서 진행한다. 07의 04 의존은 05를 통해 포함되며, 08은 07의 선행 조건을 이어받는다.

## 분해 기준

- 01의 공통 화면 위에 02·03의 입력 화면과 06의 요청 내역을 적용한다. 03은 02에서 확인한 준비·진행 표시를 재사용한다.
- 04에서 같은 탭의 입력 보관 책임을 영상·오디오에 먼저 연결하고, 05에서 실제 로컬 파일을 다루는 자막에 적용한다.
- 07은 두 입력의 보존이 완료된 뒤 내역의 접수·취소·중복 방지를 영상·오디오에 연결한다. 08은 그 처리를 자막 업로드에 확장한다.
- 각 티켓에서 사용자가 확인할 수 있는 행동과 검증을 함께 완료한다. 별도의 테스트 전용 티켓으로 검증을 미루지 않는다.

## 공통 완료 기준

- 관련 사용자 요구사항, 승인된 시안의 배치와 해당 화면의 문서 계약을 함께 반영한다. 다른 티켓이 담당하는 동작은 임의로 확대하지 않는다.
- 주 검증은 기존 브라우저 통합 시나리오를 사용한다. 취소와 늦은 성공의 경쟁·저장 실패는 기존 추출 요청 생명주기 공개 인터페이스 검증을 필요한 만큼 보강한다.
- 마지막 변경 이후 관련 정적 검사·자동 테스트·빌드·브라우저 확인 결과를 기록한다. 브라우저 명령에 포함된 빌드를 같은 변경에 중복 실행할 필요는 없다.
- 변경한 화면에서 일반 텍스트 대비 4.5:1, 큰 텍스트·조작 경계·포커스 3:1, 주요 조작 영역 44×44px와 키보드 접근을 확인한다.
- 로컬에서 통제한 응답과 브라우저 결과를 실제 처리 서비스·물리 기기·화면 낭독기 검증으로 표현하지 않는다. 전체 완료 판단은 8개 티켓의 완료 조건을 모두 충족한 뒤 한다.
- 기존 개인 사용 단계, 서버 요청·응답, 업로드 절차, 파일·내역 보존 정책과 Chrome 확장 프로그램의 계약을 유지한다.
- 현재 작업 트리에 있던 다른 변경과 상위 명세·합의 기록을 보존한다. 티켓 발행 자체를 제품 구현 완료로 기록하지 않는다.
