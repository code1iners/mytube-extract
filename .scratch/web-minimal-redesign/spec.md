# Web 최소 구성 재설계

승인된 2차 시안과 설계 인터뷰의 최종 합의를 구현 가능한 요구사항으로 정리한다. 이번 발행 범위는 명세 문서이며, 제품 코드 수정 승인은 포함하지 않는다.

## Problem Statement

Web 앱 사용자는 영상·오디오 또는 영어 자막을 추출하려고 들어왔는데, 준비 상태 설명, 공통 단계 표시, 큰 파일 선택 영역과 반복되는 카드가 실제 입력과 요청보다 많은 공간을 차지한다. 모바일에서는 파일을 선택한 뒤 제출 버튼 일부가 하단 고정 탭에 가려지기도 한다. 데스크톱의 기존 상단 탭도 작업 영역과의 관계가 명확하지 않다.

요청 내역의 `다시 요청`은 해당 종류의 입력 화면으로 이동할 뿐 이전 조건을 이어서 실행하지 못한다. 메뉴를 잠깐 오가면 미제출 주소나 파일도 사라진다. 일부 보조 텍스트의 대비와 주소 입력의 접근성 이름이 불안정하며, 완료 후에도 처리 중처럼 보이는 진행 막대가 남는다.

사용자는 설정과 설명을 다시 읽거나 여러 확인 단계를 거치지 않고, 입력하고 필요한 선택을 한 뒤 요청하고 싶다. 실패·만료된 요청도 단순한 조작으로 다시 실행하고 싶다.

## Solution

영상 추출·자막 추출·요청 내역과 공통 화면을 무채색 중심의 단순한 작업 공간으로 재설계한다. 모바일은 하단 고정 탭, 데스크톱은 왼쪽 세로 메뉴와 오른쪽 작업 영역을 사용한다. 헤더의 보조 메뉴는 가로 점 세 개 `…` 아이콘으로 표시한다.

입력과 필수 선택은 항상 보이고, 정상 준비 상태와 불필요한 단계 설명은 숨긴다. 자막 파일은 하나의 간결한 영역에서 선택·확인·변경·지우기를 처리한다. 내역은 구분선 목록으로 만들고 다운로드와 다시 요청을 바로 제공한다.

영상·오디오는 이전 조건으로 즉시 다시 요청한다. 자막은 파일만 다시 고르면 이전 처리 방식으로 실행한다. 입력 화면으로 이동하거나 별도 확인창을 띄우지 않고, 작성 중인 다른 입력도 유지한다. 메뉴 이동 중의 미제출 입력과 새로고침 후 기억할 선택값의 수명을 구분한다.

## User Stories

### 화면 구성과 탐색

1. As a Web 앱 사용자, I want 영상 추출·자막 추출·요청 내역을 같은 탐색 구조에서 찾기를 원한다, so that 작업 종류가 달라져도 위치를 다시 익히지 않는다.
2. As a 모바일 사용자, I want 하단 고정 탭으로 세 주요 화면을 오가기를 원한다, so that 엄지로 주요 작업에 접근할 수 있다.
3. As a 데스크톱 사용자, I want 왼쪽 메뉴에서 작업을 고르고 오른쪽에서 입력하기를 원한다, so that 탐색과 현재 작업을 쉽게 구분한다.
4. As a 데스크톱 사용자, I want 형식과 화질을 나란히 비교하기를 원한다, so that 짧은 입력 영역에서 요청 조건을 정한다.
5. As a Web 앱 사용자, I want 헤더의 `…`에서 기존 사용 안내와 설정에 접근하기를 원한다, so that 보조 기능이 주요 작업과 경쟁하지 않는다.
6. As a 키보드 사용자, I want 보조 메뉴를 열고 닫은 뒤 원래 조작 위치로 돌아오기를 원한다, so that 포커스를 잃지 않는다.
7. As a Web 앱 사용자, I want 시스템·라이트·다크 테마 선호를 계속 사용하기를 원한다, so that 기존 화면 선호가 재설계 후에도 유지된다.
8. As a Web 앱 사용자, I want 로고 외의 주요 조작을 무채색으로 구분하기를 원한다, so that 화면의 시각적 경쟁이 줄어든다.
9. As a Web 앱 사용자, I want 읽기 쉬운 하나의 서체와 필요한 설명만 보기를 원한다, so that 장식이나 반복 문구에 주의를 빼앗기지 않는다.

### 입력과 준비 상태

10. As a Web 앱 사용자, I want 서비스 준비 확인 중에도 주소나 파일을 입력하기를 원한다, so that 확인이 끝나기만 기다리지 않는다.
11. As a Web 앱 사용자, I want 서비스가 준비되지 않았을 때 입력은 유지되고 요청만 제한되기를 원한다, so that 장애 때문에 작성한 내용을 잃지 않는다.
12. As a Web 앱 사용자, I want 요청할 수 없는 이유와 다시 확인을 제출 위치 근처에서 보기를 원한다, so that 문제와 다음 행동을 한곳에서 이해한다.
13. As a Web 앱 사용자, I want 정상 상태의 준비됨·마지막 확인 시각·재확인 버튼이 숨겨지기를 원한다, so that 입력에 집중한다.
14. As a 영상 추출 사용자, I want 주소 입력의 이름이 입력값이나 지우기 버튼 유무와 관계없이 일정하기를 원한다, so that 보조 기술로 같은 입력을 안정적으로 찾는다.
15. As a 영상 추출 사용자, I want 주소를 지운 뒤 같은 입력에서 다시 작성하기를 원한다, so that 수정이 간단하다.
16. As a 영상 추출 사용자, I want 비디오·오디오와 각 형식의 세 품질을 바로 보기를 원한다, so that 추가 화면을 열지 않고 조건을 정한다.
17. As a 자막 추출 사용자, I want 속도 우선·정확도 우선을 바로 비교하기를 원한다, so that 원하는 처리 방향을 쉽게 고른다.
18. As a Web 앱 사용자, I want 기술 설명만 필요할 때 펼쳐 보기를 원한다, so that 기본 화면은 간결하면서도 선택의 의미를 확인할 수 있다.
19. As a 자막 추출 사용자, I want 파일 선택 전후에 같은 영역을 사용하기를 원한다, so that 파일을 골랐다고 화면이 크게 늘어나지 않는다.
20. As a 자막 추출 사용자, I want 선택한 파일명·크기·파일 변경·지우기를 한곳에서 보기를 원한다, so that 요청할 파일을 바로 확인하고 수정한다.
21. As a 데스크톱 사용자, I want 간결한 파일 선택 영역에 파일을 끌어놓기를 원한다, so that 기존 입력 방식을 계속 사용한다.
22. As a 자막 추출 사용자, I want 잘못된 파일을 끌어놓아도 기존의 유효한 파일이 유지되기를 원한다, so that 실수로 요청 대상을 잃지 않는다.
23. As a 모바일 사용자, I want 일반적인 390×844 화면에서 제출 버튼 전체를 스크롤 없이 보기를 원한다, so that 파일 선택 후에도 바로 요청한다.
24. As a 작은 화면이나 확대 화면의 사용자, I want 긴 내용은 스크롤로 읽고 마지막 조작을 하단 탭 위에서 사용하기를 원한다, so that 화면 크기가 달라도 기능이 가려지지 않는다.

### 추출 요청 생명주기

25. As a Web 앱 사용자, I want 요청 직전에 준비 상태와 입력을 확인하기를 원한다, so that 준비되지 않았거나 잘못된 요청을 보내지 않는다.
26. As a Web 앱 사용자, I want 접수 중에는 중복 실행과 다른 화면으로의 이동이 막히기를 원한다, so that 같은 요청을 실수로 여러 번 보내지 않는다.
27. As a Web 앱 사용자, I want 접수 전 요청 취소 후 입력과 조작 가능 상태를 되찾기를 원한다, so that 다시 작성하거나 다른 작업으로 이동한다.
28. As a Web 앱 사용자, I want 취소와 서버 접수가 겹쳐도 이미 만들어진 요청을 내역에서 찾기를 원한다, so that 실행 중인 요청을 놓치지 않는다.
29. As a Web 앱 사용자, I want 현재 화면에 머무르면 접수·처리·결과를 이어서 보기를 원한다, so that 별도 이동 없이 진행을 확인한다.
30. As a Web 앱 사용자, I want 실제 상태와 확인 가능한 진행률만 보기를 원한다, so that 장식용 단계나 추정 수치에 혼동하지 않는다.
31. As a Web 앱 사용자, I want 완료 후에는 결과와 다운로드를 보기를 원한다, so that 100% 막대 없이도 다음 행동을 안다.
32. As a Web 앱 사용자, I want 실패·만료·상태 조회 오류를 구분하고 가능한 복구 동작을 보기를 원한다, so that 같은 실패를 무작정 반복하지 않는다.
33. As a 자막 추출 사용자, I want 같은 화면에서 실패를 복구할 때 선택 파일을 유지하기를 원한다, so that 불필요하게 파일을 다시 고르지 않는다.
34. As a Web 앱 사용자, I want 접수 후 준비 상태 확인이 실패해도 접수된 요청의 실제 상태를 계속 보기를 원한다, so that 서비스 안내와 작업 실패를 혼동하지 않는다.

### 입력 수명과 다시 요청

35. As a Web 앱 사용자, I want 같은 탭에서 앱 메뉴를 오가는 동안 미제출 주소·파일·선택값을 유지하기를 원한다, so that 내역을 확인한 뒤 작성을 이어간다.
36. As a Web 앱 사용자, I want 새로고침 후 원본 주소·파일은 비우고 기억한 선택값만 복원하기를 원한다, so that 새 작업을 명확하게 시작한다.
37. As a Web 앱 사용자, I want 직접 바꾼 선택이나 실제 접수된 재요청의 조건만 이후 기본값에 반영되기를 원한다, so that 내역을 둘러보는 것만으로 선호가 바뀌지 않는다.
38. As a Web 앱 사용자, I want 완료 후 `새 요청`에서 원본은 비우고 현재 선택값은 유지하기를 원한다, so that 같은 종류의 다른 원본을 간단히 처리한다.
39. As a Web 앱 사용자, I want 접수한 화면을 떠났다가 돌아오면 새 입력을 준비하기를 원한다, so that 기존 요청은 내역에서 보고 다음 작업은 별도로 시작한다.
40. As a 영상·오디오 사용자, I want 실패·만료 항목의 `다시 요청`을 한 번 눌러 같은 원본·형식·품질로 실행하기를 원한다, so that 조건을 다시 입력하지 않는다.
41. As a 자막 추출 사용자, I want `다시 요청`에서 파일만 다시 고르면 이전 처리 방식으로 실행되기를 원한다, so that 별도 설정 화면과 제출 단계를 반복하지 않는다.
42. As a 자막 추출 사용자, I want 재요청의 파일 선택을 취소하면 아무 요청도 생기지 않기를 원한다, so that 취소한 행동이 실행되지 않는다.
43. As a Web 앱 사용자, I want 내역에서 다시 요청해도 작성 중인 다른 주소·파일·선택값이 유지되기를 원한다, so that 진행 중인 작성을 덮어쓰지 않는다.
44. As a Web 앱 사용자, I want 재요청이 새 항목으로 남고 원래 항목도 기존 보존 규칙대로 유지되기를 원한다, so that 이전 결과와 새 결과를 구분한다.
45. As a Web 앱 사용자, I want 재요청 접수에 실패하면 기존 내역과 입력을 유지하고 이유를 보기를 원한다, so that 무엇이 실행됐는지 오해하지 않는다.
46. As a Web 앱 사용자, I want 내역 조회·파일 선택 취소·접수 실패가 기억한 기본값을 바꾸지 않기를 원한다, so that 실패한 시도로 새 입력의 조건이 달라지지 않는다.

58. As a 처음 사용하는 사용자, I want 빈 내역에서 영상·자막 추출의 출발점과 보관 범위를 간단히 알기를 원한다, so that 어디서 시작할지 이해한다.
59. As a 키보드·보조 기술 사용자, I want 입력·선택·메뉴·상세·요청·복구를 명확한 이름과 포커스로 조작하기를 원한다, so that 마우스 없이도 같은 작업을 수행한다.
60. As a Web 앱 사용자, I want 라이트·다크에서 읽을 수 있는 대비와 충분한 조작 영역을 갖기를 원한다, so that 색이나 작은 버튼 때문에 기능을 놓치지 않는다.

## Implementation Decisions

### 1. 적용 범위와 시각 계약

- Web 앱의 영상 추출, 자막 추출, 요청 내역과 공통 레이아웃·주요 내비게이션·헤더 보조 메뉴를 함께 변경한다. 설정 화면은 공통 화면과 기존 테마 선호 접근에 영향을 받는 범위만 포함한다.
- 승인된 2차 시안의 배치와 본 명세의 행동 계약을 기준으로 한다. 시안의 파일명·시각·선택 상태·주소·진행률과 이미지에 포함된 브라우저·휴대폰 외형은 예시이며 제품 기능이나 기본값으로 복제하지 않는다.
- 브랜드 빨강은 로고 아이콘에 남긴다. 서비스 이름, 주요 버튼, 선택 표시와 내비게이션은 무채색으로 구성한다. 라이트의 주요 버튼은 짙은 회색, 다크의 주요 버튼은 밝은 회색을 사용한다.
- 오류·완료 등의 상태색은 의미 전달에 필요한 범위에서 사용하고 텍스트나 아이콘을 함께 제공한다. 상태를 색만으로 구분하지 않는다.
- Pretendard 단일 서체를 유지한다. 장식용 서체, 배경 이미지, 등장 애니메이션, 기능 없는 큰 여백이나 중첩 카드를 추가하지 않는다.
- 색·크기·간격의 세부 값은 승인된 시각 방향, 기존 토큰 구조와 접근성 기준 안에서 정한다. 이미지의 픽셀을 그대로 따라 접근성을 희생하지 않는다.
- 기존 Web·Chrome 확장 프로그램 공통 디자인 계약의 빨간 액션 색과 충돌하는 부분은 Web 전용 규칙으로 명시한다. 공통 자산을 수정해 확장 프로그램의 디자인까지 바꾸지 않는다.

### 2. 공통 레이아웃과 탐색

- 모바일은 기존 하단 고정 탭의 세 목적지를 유지한다. 데스크톱은 상단 탭을 제거하고 왼쪽 로고·세로 메뉴, 오른쪽 작업 영역으로 바꾼다.
- 기존 모바일·데스크톱 전환 경계인 820px 이하와 821px 이상을 우선 유지한다. 폭이 좁아지거나 글자를 확대하면 선택 그룹과 내용이 자연스럽게 줄바꿈되도록 한다.
- 데스크톱 영상 화면의 형식·화질 그룹은 공간이 허용될 때 나란히 놓는다. 공간이 부족하면 형식 다음 품질의 읽기 순서를 유지하며 세로로 배치한다.
- 헤더 오른쪽 보조 메뉴의 시각 표현은 가로 점 세 개 `…`만 사용한다. 접근성 이름 `더보기`, 사용 안내·설정, 열림 상태 전달, Escape와 바깥 클릭 닫기, 닫은 뒤 포커스 복귀를 유지한다.
- 현재 목적지와 접수 중 이동 잠금을 알 수 있어야 한다. 보이지 않는 모바일·데스크톱 메뉴가 키보드 탐색이나 접근성 트리에 중복 노출되지 않게 한다.
- 하단 탭 높이와 안전 여백을 본문에 반영한다. 일반적인 390×844 화면에서는 입력과 파일 선택 후 모두 제출 버튼 전체가 스크롤 없이 보인다. 긴 내용·작은 화면·글자 확대에서는 스크롤을 허용하되 끝에서 모든 조작이 탭 위로 드러나야 한다.

### 3. 입력과 준비 상태

- 영상 입력 순서는 원본 주소 → 형식 → 품질 → 추출 요청이다. 자막은 파일 → 처리 방식 → 자막 추출이다. 모바일과 데스크톱의 의미상 순서를 같게 유지한다.
- 비디오 품질 360p·720p·1080p, 오디오 품질 128·192·320 kbps, 자막의 속도 우선·정확도 우선을 유지한다. 품질 단위 kbps는 kilobits per second, 초당 데이터 전송량이다.
- 속도 우선은 기존 `base_en`, 정확도 우선은 기존 `small_en`에 대응한다. 결과는 기존 영어 SRT 자막이다. SRT는 SubRip Subtitle, 시간 정보가 포함된 자막 파일 형식이다. 언어·처리 모델·지원 파일 형식을 확대하지 않는다.
- 형식·품질·처리 방식은 항상 보이게 두고 기술 설명만 기본으로 접는다. 정상 상태의 준비됨·마지막 확인 시각·재확인 버튼은 숨긴다.
- 최초 준비 확인 중, 확인 실패, 처리 서비스 미가용에도 입력을 유지한다. 준비되지 않았으면 제출을 막고 제출 위치 근처 한곳에 짧은 상태·이유와 필요한 재확인을 제공한다. 상태 공지와 입력 검증 오류를 중복 출력하지 않는다.
- 요청 직전 준비 상태 재확인과 기존 입력 검증은 유지한다. 접수된 작업의 상태가 있으면 이후의 준비 상태 오류로 작업 결과를 덮어쓰지 않는다.
- 주소 입력의 접근성 이름을 별도 라벨로 고정한다. 설명과 지우기 버튼은 입력 이름에 합쳐지지 않으며, 값을 지우면 같은 입력으로 포커스를 돌린다.
- 자막은 하나의 간결한 선택 영역을 사용한다. 선택 후 같은 영역에 파일명·크기·파일 변경·지우기를 표시하고 별도 큰 빈 선택 영역을 추가하지 않는다. 긴 파일명은 조작과 겹치지 않게 줄바꿈할 수 있다.
- 기존 파일 선택·변경·지우기·끌어놓기 경로를 유지한다. 지원하지 않는 새 드롭은 거부하고 기존 유효 파일은 유지한다. 파일 검증·업로드 용량 오류는 입력 가까이에 표시한다.

### 4. 미제출 입력과 기억한 선택값

미제출 입력은 같은 탭의 앱 메뉴 이동을 견디는 메모리 상태로 보관한다. 화면별 검증과 포커스 처리는 해당 화면이 담당하고, 메뉴 전환보다 오래 유지할 값만 공통 보관 책임으로 분리한다. 원본 주소나 로컬 파일을 영속 저장하는 기능은 추가하지 않는다.

| 상황 | 원본 주소·파일 | 현재 선택값과 이후 기본값 | 접수된 요청 |
| --- | --- | --- | --- |
| 미제출 상태에서 앱 메뉴 이동 후 복귀 | 그대로 유지 | 작성 중 선택 그대로 유지 | 영향 없음 |
| 새로고침 | 비움 | 브라우저에 기억한 선택만 복원 | 저장된 접수증으로 내역에서 확인 |
| 직접 옵션 변경 | 유지 | 해당 선택을 현재 입력과 기억할 기본값에 반영 | 영향 없음 |
| 내역 조회·재요청 파일 선택 취소·접수 실패 | 작성 중 입력 유지 | 현재 입력과 기억한 기본값을 바꾸지 않음 | 접수 성공이 확인되지 않으면 새 접수증 없음; 늦은 성공은 아래 생명주기 규칙 적용 |
| 내역 재요청 접수 성공 | 작성 중 입력 유지 | 재사용한 조건을 이후 기본값에 기억하되 기존 초안의 선택은 변경하지 않음 | 새 접수증으로 추적 |
| 완료 후 `새 요청` | 비움 | 해당 화면의 현재 선택 유지 | 기존 요청은 내역에 유지 |
| 추출 화면에서 접수 후 다른 메뉴로 이동·복귀 | 새 입력은 비움 | 기억한 선택으로 새 입력 준비 | 이전 작업은 내역에서 계속 확인 |
| 같은 추출 화면에서 취소·오류 복구 | 기존 원본 유지 | 기존 선택 유지 | 이미 접수된 작업은 별도 상태로 유지 |

- 영상·오디오 입력과 자막 입력은 서로 구분해 보관한다. 내역 재요청용 입력도 작성 중인 추출 화면의 입력과 구분한다.
- 접수된 요청의 원본 맥락을 현재 화면에서 오류 복구에 쓰는 것과 미제출 입력을 메뉴 이동 후 복원하는 것을 혼동하지 않는다. 접수된 화면을 떠난 뒤 그 원본을 새 입력에 다시 채우지 않는다.
- 기본값 저장 시점은 직접 옵션 변경 또는 실제 재요청 접수 성공이다. 초안 복원·화면 재진입만으로 저장 효과를 실행해 다른 요청이 기억한 기본값을 덮어쓰지 않는다.
- 저장된 선호가 없다면 기존 제품 기본값인 오디오 320 kbps·자막 속도 우선을 유지한다. 형식을 직접 바꿀 때의 기존 품질 기본값인 비디오 1080p·오디오 320 kbps도 유지한다. 시안에 보이는 비디오 선택은 초기 기본값 변경 합의가 아니다.
- 저장 불가 환경에서는 현재 메모리의 입력·선택으로 작업할 수 있어야 하며, 새로고침 뒤 선택 복원을 보장한다고 안내하지 않는다.

### 5. 내역의 다시 요청

- 대상은 기존과 같이 실패·만료된 요청이다. 실행 링크를 입력 화면 이동으로 구현하지 않고 내역에서 새 요청을 시작하는 행동으로 바꾼다.
- 영상·오디오는 정상 조회된 원래 요청의 원본 주소·형식·품질로 즉시 접수를 시도한다. 여기서 즉시는 별도 입력 화면·확인창·추가 제출 없이 실행한다는 뜻이며 준비 확인이나 검증을 생략하지 않는다.
- 자막은 원래 요청의 처리 방식을 유지한 채 파일 선택을 연다. 유효한 파일을 고르면 기존 업로드·접수 절차를 시작한다. 파일 선택 취소나 검증 실패는 접수로 이어지지 않는다. 작성 중인 다른 화면의 파일을 재요청 파일로 자동 사용하지 않는다.
- 내역 화면을 유지하며 접수 중 상태와 필요한 취소·실패 안내를 재요청이 시작된 위치에서 확인할 수 있게 한다. 재요청 중에는 중복 접수를 막고 기존 접수 중 이동 잠금을 적용한다.
- 성공하면 별도 접수증으로 새 요청을 목록에 반영한다. 원래 요청의 상태·생성 시각·접수증을 새 요청처럼 덮어쓰지 않는다. 기존 최대 20건 보존 규칙은 계속 적용한다.
- 실패하거나 취소하면 기존 내역과 작성 중 입력을 유지한다. 취소와 늦은 성공 응답이 경쟁하면 기존 생명주기 규칙에 따라 이미 생성된 요청의 접수증을 보존한다.
- 상태 조회가 실패해 조건을 확보하지 못한 경우에는 요청 실패·만료로 추정해 재요청하지 않는다. 조회 복구 동작을 유지한다. 서버에 요청 기록이 없어 404를 받은 경우에는 기존 접수증 정리 규칙을 따른다.
- 영상의 원본 주소는 서버가 제공하는 정규화된 주소를 사용한다. 이전에 입력한 주소의 부가 질의 문자열까지 복원하는 기능은 추가하지 않는다.
- 다시 요청은 이전 서버 작업의 재개나 자동 재시도와 다르다. 입력을 불러온 뒤 확인·제출하는 중간 단계와 입력 덮어쓰기 확인창은 추가하지 않는다.

### 6. 모듈 책임과 서버 계약

- 공통 화면 모듈은 데스크톱 메뉴·모바일 탭·보조 메뉴·테마를 담당한다. 각 추출 화면은 입력 검증·파일 선택·표시·포커스를 담당한다. 미제출 입력 보관은 앱 메뉴 전환 수명을 담당한다.
- 기존 `추출 요청 생명주기` 모듈의 준비 확인·접수·이동 잠금·접수 전 취소·늦은 접수 결과·접수증 저장·상태 조회 책임을 유지한다. 내역 재요청에서도 이 책임과 영상·자막 어댑터를 재사용할 수 있도록 연결한다.
- 영상·자막의 재요청마다 별도의 생명주기 구현을 복제하지 않는다. 목록의 각 항목에서 준비 확인과 새 접수 제어를 독립적으로 반복 생성하는 구조도 피한다.
- 자막 파일의 분할 업로드 시작·부분 전송·완료·실패 정리는 기존 자막 어댑터 안에 둔다. 새 화면이나 내역 항목이 통신 순서를 직접 조합하지 않는다.
- 준비 상태가 입력을 숨기던 기존 화면 규칙과 메뉴 이동 시 미제출 입력이 소멸하던 기존 화면 수명은 본 명세로 변경한다. 기존 구조 개선 명세의 동작 보존 문구를 근거로 이번에 승인된 변경을 누락하지 않는다.
- 서버 API는 Application Programming Interface, 화면과 서버가 주고받는 요청·응답 규약을 뜻한다. 이번 작업은 기존 서버 API와 데이터베이스 구조를 변경하지 않는다.

| --- | --- |
| 준비 상태 조회 | 입력을 유지한 채 접수 가능 여부 판단 |
| 영상·오디오 요청 생성 | 새 입력 또는 내역의 원래 주소·형식·품질로 새 작업 생성 |
| 영상·오디오 상태 응답의 `sourceUrl`, `type`, `quality` | 직접 재요청 조건의 근거 |
| 자막 상태 응답의 `fileName`, `whisperModel` | 대상 식별과 이전 처리 방식의 근거; 로컬 파일 자체는 다시 선택 |
| 자막 분할 업로드·완료·정리 | 새 입력과 내역 재요청이 동일한 기존 절차 사용 |
| 상태·진행률·메시지·다운로드 주소·보관 기간 | 서버 응답에 근거해 현재 작업과 내역 표시 |

- 새 재요청 서버 명령, 서버 작업 취소, 요청 연결용 스키마나 계정 모델을 도입하지 않는다. 기존 개인 사용 단계와 YouTube 추출 방식에 관한 결정은 유지한다.

### 7. 요청 내역과 결과 표시

- 외곽 카드 반복을 없애고 구분선 목록을 사용한다. 제목·종류·품질 또는 자막 처리 방식·시각·상태·주요 행동은 접지 않는다. 상세 설명과 삭제만 펼쳐서 접근한다.
- 요청 영상 제목이 있으면 기존 제목을 보여주고, 없으면 접근 가능한 원본 주소로 식별한다. 긴 제목·주소·파일명을 읽을 수 있게 유지한다.
- 공통 `원본 → 추출 → 파일 수령` 단계 표시는 요청 화면과 내역에서 제거한다. 접수·처리 중에는 실제 단계와 확인 가능한 진행률을 표시하고, 진행률을 알 수 없으면 임의의 퍼센트를 만들지 않는다.
- 완료 화면과 완료 내역에는 100% 막대를 남기지 않는다. 결과·형식·필요한 보관 안내와 실제 다운로드를 제공한다. 완료 응답에 다운로드 주소가 없으면 정상 다운로드처럼 표시하지 않고 기존 조회 복구를 유지한다.
- 접수증에는 기존 종류·작업 식별자·접수 시각만 보관한다. 원본 파일·화면 상태·제목·재요청 조건을 접수증에 추가 저장하지 않는다. 최신 접수순 최대 20건, 다른 탭의 변경 반영과 직접 내역 연결을 유지한다.
- 처리 중 요청은 기존 정책으로 조회하고 완료·실패·만료는 주기적 조회를 멈춘다. 일시적 네트워크·서버 오류에서는 접수증을 유지하고 404에서만 해당 항목을 제거한다.
- 저장 실패가 서버 요청 실패로 바뀌지 않아야 한다. 현재 세션에서 접수된 요청의 내역 연결을 유지하되, 새로고침 후 복구까지 보장하지 않는다.
- 내역 삭제는 접수증 삭제이며 서버 작업 취소가 아니다. 기존 최근 한 건의 8초 되돌리기, 저장 실패 안내와 다른 탭 동기화를 유지한다.
- 삭제가 접힌 상세로 이동하므로 삭제 후 포커스는 실제 보이는 다음 항목의 조작, 이전 항목의 조작, 목록 제목 순으로 안전하게 복귀시킨다. 닫힌 상세 속 버튼에 포커스를 보내지 않는다. 되돌린 항목은 식별 가능한 제목이나 첫 조작으로 포커스를 복구한다.
- 빈 내역의 영상·자막 시작점, 현재 브라우저에 남는 내역과 기존 완료 파일 보관 안내를 유지한다. 시안의 예시 자료를 근거로 목록 정렬·보존 정책을 바꾸지 않는다.

### 8. 접근성과 문서 동기화

- 일반 텍스트 대비는 4.5:1 이상, 큰 텍스트와 필요한 조작 경계·초점 표시는 3:1 이상을 확보한다. 브랜드 로고 예외를 일반 안내문이나 버튼 텍스트에 적용하지 않는다.
- 메뉴, 지우기, 파일 변경, 다운로드, 다시 요청, 상세, 삭제·되돌리기 등 주요 조작은 실제 클릭 영역 44×44px 이상을 확보한다. 작은 아이콘으로 바꿔도 조작 영역을 줄이지 않는다.
- 입력의 이름·설명·오류 관계, 선택 상태, 메뉴의 열림 상태, 현재 목적지, 상태 공지와 이동 잠금 사유를 보조 기술에 전달한다. 키보드와 시각적 읽기 순서를 맞춘다.
- 화면·내비게이션·준비 상태·내역 동작이 바뀌면 관련 Web 디자인 계약과 화면 설명을 함께 갱신한다. 기존 문서의 상단 탭·입력을 숨기는 준비 화면·공통 단계 표시·입력 화면으로 이동하는 재요청 설명을 새 동작과 일치시킨다.

## Testing Decisions

좋은 테스트는 사용자가 보는 내용, 입력·선택·포커스, 메뉴 이동 뒤의 결과, 서버로 전달하는 요청, 접수증과 기본값의 변화를 검증한다. 내부 상태 변수·효과 실행 순서·스타일 클래스·컴포넌트 개수를 그대로 복제한 검증이나 생성 이미지와의 기계적 픽셀 일치를 합격 기준으로 삼지 않는다.

### 검증 지점

- **주 검증 지점은 기존 Web 브라우저 통합 시나리오다.** 실제 앱을 Playwright의 Chromium에서 열고 서버 응답만 통제한다. 영상·자막·요청 내역·설정 이동, 파일 선택, 준비 상태, 재요청, 접수증 저장과 반응형 배치를 이 한 경계에서 함께 검증한다.
- **기존 추출 요청 생명주기 공개 인터페이스 테스트를 보강한다.** 취소와 늦은 성공의 경쟁, 저장 실패, 요청·상태 조회 오류 우선순위처럼 시간과 응답 순서가 중요한 경우에 기존 메모리 어댑터를 사용한다. 새 내부 테스트 지점을 늘리지 않는다.
- 요청 선호·접수증·파일 검증의 기존 계약 테스트는 해당 규칙을 수정하는 경우에만 보강한다. 단순 레이아웃 변경을 이유로 같은 행동을 작은 컴포넌트마다 중복 테스트하지 않는다.
- 기존 선례는 브라우저의 준비 상태·파일 선택·취소·저장 실패·내역 제목·반응형 내비게이션 시나리오, 생명주기의 비동기 응답 제어 테스트, 요청 선호의 저장·손상값·저장 차단 테스트다. 새로운 프레임워크나 서버 테스트용 명령을 추가하지 않는다.

### 화면 검증과 실행 기준

- 기본 크기는 320px·390px·1280px 폭을 사용하고, 모바일·데스크톱 전환인 820px·821px도 확인한다. 390×844의 일반 입력·파일 선택 전후에서 전체 제출 버튼이 최초 화면에 들어오는지 실제 브라우저 좌표로 검증한다.
- 긴 제목·파일명과 200% 글자 확대에서는 안전한 줄바꿈·스크롤과 조작 가능성을 확인한다. 단순 화면 캡처 축소를 글자 확대 검증으로 대신하지 않는다.
- 라이트·다크 각각 대표 입력·처리·완료·실패·내역 화면을 실제 브라우저에서 보고 승인된 시안의 배치와 의미상 차이를 점검한다. 이미지의 정확한 서체·색상·픽셀은 합격 기준이 아니다.
- 구현 완료 시 마지막 변경 이후 Web 정적 검사, 기존 단위 테스트, 빌드, 브라우저 통합 시나리오를 실행한다. 기존 명령은 `pnpm --filter web run lint`, `pnpm --filter web run test`, `pnpm --filter web run build`, `pnpm run test:web:browser`다. 브라우저 명령이 빌드를 포함하므로 같은 변경에 불필요한 중복 빌드를 요구하지 않는다.
- 기존 테스트가 상단 탭·준비 화면의 입력 숨김·공통 단계·입력 화면으로 이동하는 재요청을 기대하면, 이번 명세에 맞게 기대 결과를 바꾼다. 취소·저장·접근성 등 유지해야 할 행동 검증은 함께 남긴다.
- 로컬에서 통제한 서버 응답과 Chromium 결과, 실제 서버·처리 서비스·파일 저장소·물리 기기·실제 화면 낭독기 결과를 구분한다. 실제 환경에서 수행하지 않은 검증을 통과로 기록하지 않는다.

## Out of Scope

- 이번 명세 발행 중 제품 코드·스타일·테스트 코드 수정, 구현 테스트 실행, 커밋·푸시·배포.
- 별도 구현 티켓의 분해·발행. 이 문서는 하나의 기능 명세다.
- Chrome 확장 프로그램·Popup의 화면과 동작 변경.
- 서버 요청·응답, 데이터베이스 스키마, 처리 작업자, YouTube 추출 방식, Whisper 처리 모델·언어, 파일 형식·용량·보관 기간 정책 변경.
- 로그인·계정·사용자별 소유권·공개 서비스 전환·다른 기기 간 동기화.
- 원본 주소·로컬 파일의 영속 저장, 새로고침 후 원본 복원, 여러 탭 사이의 미제출 입력 동기화.
- 이전 서버 작업의 재개·취소, 자동 재요청, 완료 항목 재요청이나 일괄 실행·삭제 등의 새 기능.
- 내역 재요청의 입력 화면 복원·확인 후 제출·초안 덮어쓰기 확인창.
- 검색·필터·대시보드·사이드바 접기 등 합의하지 않은 탐색 기능, 설정 항목 확대.
- 장식용 이미지·추가 서체·등장 애니메이션, 아이콘 라이브러리 교체 자체, 새 테스트 체계 도입.

## Further Notes

- 결정 근거는 [최종 설계 합의](decisions.md)와 [승인된 2차 시안](mockups/v2/README.md)이다. 생성 입력은 시안 재현 자료이며 사용자 요구나 제품 구현 지시를 추가하는 근거가 아니다.
- [기존 디자인 계약](../../docs/DESIGN.md)의 Web·확장 공통 빨간 액션 색, [기존 레이아웃 명세](../web-layout-modernization/spec.md)의 상단 탭·준비 상태·단계 표시, [기존 추출 요청 생명주기 명세](../extraction-request-lifecycle/spec.md)의 화면별 입력 수명 중 본 명세와 충돌하는 부분은 이번 승인 범위에서 갱신한다.
- [개인 사용 단계 결정](../../docs/adr/0001-keep-single-user-mode-until-public-service-transition.md)과 [YouTube 추출 방식 결정](../../docs/adr/0002-youtube-default-client-with-web-embedded-fallback.md)은 변경하지 않는다.
- 현재 코드에는 라우트에 묶인 원본 입력, 선택값의 자동 저장 효과, 입력 화면으로 이동하는 내역 재요청이 남아 있다. 상태 응답에는 직접 재요청에 필요한 영상 조건과 자막 처리 방식이 이미 있다. 이 사실을 기준으로 Web 내부 연결과 상태 수명을 변경한다.
- `ready-for-agent`는 구현 가능한 명세로 로컬 이슈 트래커에 등록됐다는 뜻이다. 사용자의 기존 코드 수정 금지 지시는 별도 구현 요청 전까지 유지한다.
- 1차·2차 시안은 정적 생성 이미지다. 이번 명세 발행은 이미지나 제품의 실제 동작을 검증했다는 뜻이 아니다. 기존 작업 트리의 다른 변경을 보존하고 이 명세와 관련 기록만 작성한다.
