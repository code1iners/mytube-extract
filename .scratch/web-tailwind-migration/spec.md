# Web 앱 Tailwind CSS 전환

## 문제 정의 (Problem Statement)

Web 앱의 스타일은 디자인 토큰과 화면별 선택자, 상태별 규칙, 반응형 규칙을 전역 스타일에 함께 정의하는 방식으로 관리된다. 유지보수자는 화면 구조와 실제로 적용되는 스타일을 서로 다른 위치에서 확인해야 한다. 사용자는 Web 앱의 스타일을 Tailwind CSS로 관리하기를 원한다.

이번 작업의 목적은 스타일 작성·관리 방식을 바꾸는 것이다. 기존 디자인에 대한 개선 요청이나 새로운 제품 기능 요구가 아니므로, 전환 과정에서 화면 모양과 추출 요청 생명주기를 바꾸지 않아야 한다.

## 해결 방안 (Solution)

Web 앱의 레이아웃·간격·색상·반응형 스타일을 Tailwind 유틸리티 클래스로 옮긴다. 전역 스타일에는 디자인 토큰·폰트·기본 규칙·필요한 특수 효과만 남긴다. 기존 클래스에 `@apply`를 붙이는 것만으로 전환을 완료하지 않는다.

공통 기반, 영상·자막 요청, 요청 내역·설정 순서로 전환하고 단계마다 검증한다. 모든 단계에서 현재 디자인, 테마 선호, 접근성 및 사용자 동작을 유지한다. Chrome 확장 프로그램과 Popup은 이번 전환 대상이 아니다.

## 사용자 이야기 (User Stories)

1. 유지보수자로서, 화면 구조 가까이에서 Tailwind 유틸리티로 스타일을 읽고 수정하여 해당 화면의 배치를 이해하고 싶다.
2. 유지보수자로서, Web 앱의 일반 화면 스타일을 일관된 방식으로 작성하여 전역 선택자와 유틸리티 사이를 계속 오가며 관리하지 않고 싶다.
3. 유지보수자로서, 기존 역할별 디자인 토큰을 재사용하여 같은 역할의 색상과 표면이 화면마다 달라지지 않게 하고 싶다.
4. 유지보수자로서, 폰트·기본 규칙·특수 효과의 전역 정의를 구분하여 전역 스타일의 책임을 명확히 하고 싶다.
5. 유지보수자로서, 기존 스타일과의 공존을 전환 중에만 허용하여 각 단계를 검증하면서 최종적으로 이전 화면 스타일을 정리하고 싶다.
6. 유지보수자로서, 공통 기반을 먼저 전환하여 여러 화면에 영향을 주는 회귀를 초기에 발견하고 싶다.
7. Web 앱 사용자로서, 전환 후에도 익숙한 색상·폰트·간격·배치를 유지하여 사용 방법을 다시 익히지 않고 싶다.
8. Web 앱 사용자로서, 영상 추출 화면에서 기존 순서대로 주소와 추출 옵션을 입력하여 같은 요청을 접수하고 싶다.
9. Web 앱 사용자로서, 자막 추출 화면에서 파일과 처리 방식을 기존 방식으로 선택하여 같은 자막 추출 요청을 접수하고 싶다.
10. Web 앱 사용자로서, 준비 상태 확인과 요청 가능 여부를 기존처럼 구분하여 지금 할 수 있는 동작을 이해하고 싶다.
11. Web 앱 사용자로서, 접수 전 요청 중단과 접수 후 상태 추적의 기존 동작을 유지하여 스타일 전환으로 요청이 유실되거나 중복되지 않게 하고 싶다.
12. Web 앱 사용자로서, 처리 중·완료·실패·만료 상태의 안내와 가능한 동작을 기존처럼 확인하고 싶다.
13. Web 앱 사용자로서, 완료 결과와 다운로드 동작을 기존처럼 이용하여 파일을 받을 수 있고 싶다.
14. Web 앱 사용자로서, 요청 내역의 빈 상태와 기록이 있는 상태를 기존처럼 확인하여 이전 요청을 관리하고 싶다.
15. Web 앱 사용자로서, 요청 내역 삭제와 되돌리기 동작을 기존처럼 이용하여 브라우저에 남은 내역을 관리하고 싶다.
16. Web 앱 사용자로서, 설정에서 시스템·라이트·다크 테마 선호를 유지하고 다음 방문에도 기존처럼 복원하고 싶다.
17. 모바일 Web 앱 사용자로서, 좁은 화면에서도 입력·버튼·하단 내비게이션이 겹치거나 가로로 넘치지 않게 사용하고 싶다.
18. 데스크톱 Web 앱 사용자로서, 기존 본문 최대 폭과 정렬을 유지하여 동일한 화면 구성을 이용하고 싶다.
19. 키보드 사용자로서, 기존 탐색 순서와 포커스 표시를 유지하여 링크·폼·펼침 영역을 조작하고 싶다.
20. 확대 기능 사용자로서, 글자를 확대해도 핵심 안내와 조작 요소에 접근하고 싶다.
21. 움직임 감소 설정 사용자로서, 전환 후에도 기존 움직임 감소 처리를 유지하고 싶다.
22. 검토자로서, 같은 상태·테마·화면 폭의 전환 전후 증거를 비교하여 디자인 보존 여부를 판단하고 싶다.
23. 검토자로서, 자동 검사와 실제 환경 검증의 증거를 구분하여 확인하지 않은 환경까지 성공했다고 오해하지 않고 싶다.
24. Chrome 확장 프로그램 사용자로서, Web 앱의 스타일 전환 때문에 Popup의 디자인이나 동작이 바뀌지 않기를 원한다.

## 구현 결정 (Implementation Decisions)

- **대상 모듈:** Web 앱의 스타일 빌드 연결, 디자인 토큰 연결, 공통 화면 구조와 내비게이션, 공통 표시 컴포넌트, 영상·자막 요청 화면, 요청 내역 및 설정 화면을 전환한다. 해당 화면의 오류·빈 상태·펼침 영역·사용 안내·결과 표시도 포함한다.
- **보존 기준:** 구현 착수 시점의 최신 디자인 계약과 실제 동작을 확인하고 전환 전 기준을 확보한다. 현재 별도 작업으로 수정된 코드와 문서를 보존하며, 과거 문서나 테스트를 근거로 제거된 기능을 복원하지 않는다. 문서와 실제 표시가 충돌하면 차이를 기록하고 임의의 디자인 변경으로 해소하지 않는다.
- **스타일 작성 방식:** 레이아웃·간격·색상·반응형 및 일반 상태 스타일은 Tailwind 유틸리티로 표현한다. 전역 클래스 전체를 `@apply`로 다시 작성하는 방식은 채택하지 않는다. 남는 전역 규칙은 토큰·폰트·기본 규칙·필요한 특수 효과라는 책임을 설명할 수 있어야 한다.
- **디자인 토큰:** 기존 역할별 토큰의 의미와 값을 보존하고 Tailwind 스타일에서 참조할 수 있게 연결한다. 화면마다 색상 값을 복제하거나 기본 팔레트로 교체하지 않는다. 공통 디자인 계약의 변경이 Popup에 영향을 주지 않도록 Web 앱의 구현 연결과 공통 시각 값을 구분한다.
- **테마 선호:** 시스템·라이트·다크 선택, 저장 방식, 초기 적용 및 테마 변경 동작을 유지한다. 기존 테마 상태를 스타일 선택에 연결하며 별도의 테마 상태 모델을 만들지 않는다.
- **시각 보존:** 폰트·크기·행간·간격·테두리·모서리·그림자·본문 최대 폭·반응형 전환점·상태별 표시를 유지한다. Tailwind 기본값에 맞추기 위해 현재 값을 바꾸지 않는다. 기본 스타일 초기화와 스타일 우선순위가 폼·버튼·제목 등의 모양을 바꾸지 않도록 확인한다.
- **상태별 스타일:** 선택·비활성·오류·진행·현재 위치·포커스 등 기존 상태와 스타일 연결을 보존한다. 개발 서버에서만 보이고 배포용 빌드에서는 빠지는 상태별 스타일이 없도록 검증한다.
- **동작 계약:** 요청 입력과 검증, 접수·중단·상태 추적, 완료 결과, 요청 내역 보관·삭제·되돌리기, 화면 이동과 테마 선호를 유지한다. 서버 요청·응답, 데이터 구조, 저장 키와 보존 정책을 변경하지 않는다.
- **컴포넌트 경계:** 기존 컴포넌트와 동작 인터페이스를 우선 사용한다. Tailwind 전환을 이유로 별도의 컴포넌트 라이브러리나 새로운 제품 기능을 도입하지 않는다.
- **접근성:** 의미 있는 문서 구조, 접근 가능한 이름, 상태 공지, 키보드 조작과 실제 포커스 이동, 포커스 표시, 터치 영역 및 움직임 감소 규칙을 유지한다.
- **단계 1 — 공통 기반:** 전환 전 증거를 확보한 뒤 빌드·토큰·테마 연결과 공통 화면 구조·내비게이션·공통 표시 요소를 전환한다. 전체 화면에 미치는 영향을 확인한 후 다음 단계로 진행한다.
- **단계 2 — 영상·자막 요청:** 입력 화면과 추출 요청 생명주기의 관련 표시 상태를 전환하고 요청 조작 및 상태 변화가 유지되는지 확인한다.
- **단계 3 — 요청 내역·설정:** 빈 내역·기록·삭제·되돌리기와 테마 선호 화면을 전환한다. 더 이상 쓰이지 않는 이전 화면 스타일을 제거하고 Web 앱 전체를 검증한다.
- **공존과 완료:** 중간 단계에서 이전 스타일과 Tailwind의 공존은 허용한다. 최종 완료 시 일반 화면 스타일의 이중 정의와 사용하지 않는 이전 규칙을 남기지 않는다. 테스트용 식별자 등 동작상 의미가 있는 속성은 단순히 스타일 클래스가 줄었다는 이유로 제거하지 않는다.
- **기술 선택 경계:** Tailwind 사용은 확정했으며 특정 버전이나 추가 스타일 보조 패키지는 이 논의에서 확정하지 않았다. 구현 시 현재 빌드 환경과의 호환성을 확인하고 의존성과 잠금 파일에 선택을 고정한다.

## 검증 결정 (Testing Decisions)

Q5에서 합의한 기존 자동 검사와 브라우저 기반 시각·조작 검증을 적용한다. 좋은 테스트는 특정 유틸리티 문자열이나 내부 컴포넌트 구현보다 사용자가 보는 배치·상태·동작을 검증한다.

- **주 검증 경계:** 기존 요청·요청 내역 브라우저 smoke 테스트를 중심으로 한다. 이미 테스트용 서버 응답, 화면 이동, 요청 상태, 브라우저 저장소, 테마, 반응형 배치와 포커스를 다루므로 이를 확장한다. 새로운 테스트 프레임워크나 스타일 전용 내부 테스트 계층을 만들지 않는다.
- **기존 보조 검사:** 영상·자막 요청 화면, 추출 요청 생명주기, 요청 내역, 주요 내비게이션, 설정과 테마 선호의 기존 단위 테스트를 유지한다. 클래스 변경 때문에 선택자 조정이 필요해도 사용자 행동에 대한 검증을 삭제하거나 약화하지 않는다. 가능한 경우 역할과 접근 가능한 이름을 사용한다.
- **전환 전 기준:** 각 단계의 변경 전에 같은 브라우저·폰트 로딩·테스트 데이터·상태로 화면과 주요 배치를 기록한다. 시간·진행률 등 변동 요소를 통제하여 전환 전후 비교가 가능하게 한다. 기존 실패가 있다면 먼저 기록하여 전환으로 발생한 회귀와 구분한다.
- **화면·테마 행렬:** 영상 추출·자막 추출·요청 내역·설정을 라이트·다크 각각 320×844, 390×844, 1280×900에서 비교한다. 기존 반응형 전환점의 직전·직후도 해당 규칙을 옮길 때 확인한다. 시스템 테마 선호에 따른 적용과 저장된 선호 복원은 별도로 검증한다.
- **상태 행렬:** 요청 준비 상태의 확인 중·준비 완료·확인 실패·작업 처리기 미가용, 입력 오류, 접수 중과 중단, 접수 후 진행·완료·실패·만료, 결과 동작, 빈 내역·기록이 있는 내역·삭제와 되돌리기를 기존 응답 fixture로 확인한다. 펼침 영역과 선택·비활성·포커스 상태도 포함한다. 서로 다른 클래스 문자열을 전수 검사하는 방식으로 대체하지 않는다.
- **시각 판단:** 색상·폰트·행간·간격·정렬·크기·가시성 및 표면 구분이 보존되어야 한다. 수평 넘침, 잘림, 주요 버튼과 하단 내비게이션의 겹침, 기본 스타일 초기화에 따른 폼 외형 변경이 없어야 한다. 스크린샷 비교와 필요한 실제 배치 측정을 함께 사용하며, 브라우저 렌더링 오차와 실제 회귀를 구분한다.
- **키보드·접근성:** 탭 탐색, 링크·버튼·폼·펼침 영역 조작, 실제 포커스 이동과 복귀, 포커스 표시를 확인한다. 정적 접근성 속성의 존재만으로 조작 성공을 판단하지 않는다. 기존 200% 글자 확대·터치 영역·움직임 감소 계약도 보존한다.
- **정적·자동 완료 조건:** 마지막 관련 변경 이후 Web 앱의 타입 정적 검사, 전체 단위 테스트, 배포용 빌드와 기존 브라우저 smoke가 통과해야 한다. 배포용 빌드가 생성하는 상태별 스타일과 기존 앱 패키징 검증도 유지한다.
- **단계별 실패 처리:** 영향을 받은 화면에 디자인 또는 동작 회귀가 남으면 다음 단계로 넘기지 않는다. 해당 단계의 스타일 연결을 수정하고 실패한 경계를 다시 검증한다. 관련 없는 기존 작업을 덮어쓰는 일괄 복구는 하지 않는다.
- **증거 경계:** 테스트용 응답과 로컬 브라우저 결과는 실제 서버·작업 처리기·다운로드 제공자·외부 저장소의 성공을 증명하지 않는다. 물리 모바일 기기의 브라우저 영역·안전 여백, 실제 화면 낭독기, 운영 환경을 확인하지 않았다면 미검증으로 명시한다.
- **최종 완료 조건:** 세 전환 단계 완료, 이전 일반 화면 스타일 정리, 최신 자동 검사 통과, 합의한 시각·조작 비교 완료, 남은 전역 규칙과 미검증 환경의 기록을 함께 충족해야 한다.

## 범위 밖 (Out of Scope)

- Chrome 확장 프로그램, Popup 및 YouTube 화면 위 표시 요소의 Tailwind 전환.
- 디자인 개선·브랜드 변경·토큰 값 변경·문구 개편·새 화면이나 새 기능 추가.
- 기존에 제거된 단축키 등 과거 기능의 복원.
- 서버·작업 처리기·추출 제공자·저장소·데이터 구조 및 요청 계약 변경.
- 로그인·사용자 계정·서버 기반 요청 소유권·기기 간 동기화. 기존 개인 사용 단계 결정은 유지한다.
- 별도의 컴포넌트 라이브러리 도입이나 스타일과 무관한 구조 개편.
- 이번 스펙 작성 턴에서의 코드 구현, 의존성 설치, 작업 티켓 작성, 커밋·푸시·배포.

## 추가 사항 (Further Notes)

- 2026-09-07 사용자가 Q1~Q5와 전체 전환 방침을 확정하고, 구현 없이 스펙을 먼저 작성하도록 요청했다. 추가 인터뷰 없이 합의 내용을 종합했다.
- 근거: [합의 기록](./decisions.md), [제품 용어](../../CONTEXT.md), [Web 제품 계약](../../apps/web/PRODUCT.md), [디자인 계약](../../docs/DESIGN.md), 현재 Web 앱 코드와 단위·브라우저 테스트.
- 기존 [개인 사용 단계 결정](../../docs/adr/0001-keep-single-user-mode-until-public-service-transition.md)과 [추출 제공자 대체 경로 결정](../../docs/adr/0002-youtube-default-client-with-web-embedded-fallback.md)을 변경하지 않는다.
- 기존 검증 선례는 [Web 작업 레이아웃 현대화 스펙](../web-layout-modernization/spec.md)의 브라우저 중심 검증이다. 과거 스펙의 기능 목록보다 최신 코드와 디자인 계약을 우선한다.
- 저장소의 로컬 마크다운 이슈 추적 규칙에 따라 이 문서를 게시하고 `ready-for-agent` 상태를 적용했다. 이 상태는 명세의 준비 상태이며 사용자의 별도 구현 금지 요청을 해제하지 않는다.
- 스펙 작성 시점에 별도 코드·디자인 문서 변경이 작업 트리에 존재했다. 이를 수정하거나 되돌리지 않았으며 구현 착수 때 기준을 다시 확인해야 한다.
