# 긴 영상 자막 실패 원인과 개선안

조사일: 2026-09-09. 대상 코드: `2275359`. 요청 범위는 원인 분석과 개선 조사이며 제품 코드, 실행 설정, 작업 상태는 변경하지 않았다.

## 확인된 직접 원인

화면의 작업 `8ee06733-9539-407a-a2e6-734812ae05e4`를 현재 worker 환경으로 연결한 데이터베이스에서 읽었다. 저장된 실패는 다음과 같다.

```text
status=failed
errorCode=AUDIO_TOO_LARGE
errorDetail=subtitle audio is too large: 635661494 bytes
sourceSizeBytes=772323424
whisperModel=base_en
createdAt=2026-09-09T02:20:01.511Z
startedAt=2026-09-09T02:20:04.614Z
```

현재 `apps/worker/.env`의 `SUBTITLE_AUDIO_MAX_BYTES`는 `536870912`이며 기본 상수와 Compose 기본값도 같다. 배포 worker 프로세스의 당시 환경과 바이너리는 직접 확보하지 않았다. 다만 실제 저장된 오류 문자열과 크기가 현재 함수 재현 결과와 정확히 일치한다.

[처리 순서](../../apps/worker/src/main.ts#L460)는 원본 다운로드 → 전체 음성 변환 → 파일 크기 검사 → transcribing 상태 변경 → Whisper 실행이다. [크기 검사](../../apps/worker/src/main.ts#L607)에서 한도를 초과하면 위 오류가 발생한다. 음성 인식에 도달하기 전의 차단이며, 선택된 모델의 인식 실패나 인식 실행시간 초과가 이번 코드의 직접 발생 원인은 아니다.

[현재 제품 문서](../../docs/api/current-implementation-prd.md#L45)도 긴 영상 분할 미지원과 크기 초과 실패를 명시한다. 따라서 현재 계약대로 작동한 제한이며 긴 영상 지원을 추가하는 개선 과제다.

## 길이와 크기의 관계

현재 변환 인수 `-vn -ac 1 -ar 16000 audio.wav`를 로컬 FFmpeg로 실행했다. 10초 합성 무음 입력의 ffprobe 결과:

```text
codec_name=pcm_s16le
sample_rate=16000
channels=1
bits_per_sample=16
duration=10.000000
size=320078
```

WAV (영문 원문: Waveform Audio File Format: 음성 파일 형식)의 실제 데이터가 PCM (영문 원문: Pulse-Code Modulation: 비압축 음성 표본) 16비트이므로 초당 16,000 × 1 × 2 = 32,000바이트다. MiB (영문 원문: mebibyte: 1,048,576바이트 단위)를 사용하면 다음과 같다.

| 항목 | 크기 | 이 변환 형식에서 대응하는 길이 |
|---|---:|---:|
| 현재 한도 | 536,870,912바이트 / 512MiB | 약 4시간 39분 37초 |
| 실제 실패 음성 | 635,661,494바이트 / 606.21MiB | 약 5시간 31분 4초 |
| 초과량 | 98,790,582바이트 / 94.21MiB | 약 18.4% 초과 |

길이는 헤더를 제외한 크기 환산이며 원본 메타데이터를 직접 읽은 결과는 아니다. 원본 압축 파일의 용량·영상 해상도와 추출 WAV 용량은 별개다. 같은 음성 길이를 유지한 채 영상 화질이나 업로드 비트레이트를 낮춰도 이 경로는 같은 음성 형식으로 다시 변환한다. 모델 선택 역시 크기 검사 이후이므로 이 오류를 해결하지 않는다.

## 재현과 가설 검증

조사 당시 임시 재현 도구로 TypeScript 소스의 `processSubtitleJob`, `assertSubtitleAudioSize`와 worker 로직을 읽어 격리 실행했다. 다운로드·음성 변환·음성 인식·외부 저장소는 대역이고 실제 파일 stat과 처리 순서, 실패 코드 분기는 실제 구현이었다. 측정된 크기의 희소 파일을 사용하고 종료 시 삭제했으며 네트워크나 데이터베이스 쓰기는 하지 않았다. 아래는 당시 실행 결과다.

```text
bytes=635661494 limit=536870912 status=failed
errorCode=AUDIO_TOO_LARGE transcribeCalls=0
errorDetail=subtitle audio is too large: 635661494 bytes
RED: 자막 생성에 도달하지 못함
exit=1
```

동일 조건으로 반복 실행해 같은 결과를 확인했다. 성공 기대 조건에 도달하지 못했으므로 종료 코드는 1이었다.

| 변경 변수 | 실행 인수 | 결과 |
|---|---|---|
| 기본 실패 기록 | 인수 없음 | 동일 오류, 음성 인식 0회 |
| 크기를 한도 + 1바이트로 축소 | `536870913` | 동일 오류 |
| 크기를 한도와 같게 축소 | `536870912` | 검사 통과, 음성 인식 대역 1회 |
| 원래 크기를 유지하고 한도만 640MiB로 상향 | `635661494 671088640` | 검사 통과, 음성 인식 대역 1회 |

검증한 가설은 (1) 앱의 크기 제한, (2) 길이에 비례하는 비압축 변환 용량, (3) 모델·시간 제한이다. 첫 두 가설이 기록과 실험으로 설명되며 세 번째는 이번 직접 원인에서 배제된다. 한도 상향 실험의 성공은 검사 통과만 증명한다. 실제 장시간 인식 성공을 증명하지 않는다.

## 개선 선택지

### 1. 단기: 제한적인 한도 상향

이번 파일만 크기 검사를 통과시키는 예시는 `SUBTITLE_AUDIO_MAX_BYTES=671088640`(640MiB)이다. 실제 적용 전 실행 worker의 메모리·임시 디스크·다른 대기 작업을 확인하고 긴 입력을 한 건씩 측정해야 한다. 파일 용량은 프로세스 메모리 요구량과 같지 않다. 음성 배열과 인식 작업 메모리가 추가된다.

가장 싼 검증은 실제 운영 모델로 10~30분 대표 구간을 실행하여 처리 속도와 최대 메모리를 측정하는 것이다. 이는 전체 실행시간 추정에만 사용하고 장시간 원본 검증을 대체하지 않는다. 충분한 자원 여유가 없거나 대기 작업 지연이 허용 범위를 넘으면 확대를 중단한다. 복구는 기존 한도로 되돌리고 진행 중 작업을 안전하게 종료·정리한 뒤 worker를 재시작한다. 설정 변경은 이미 실패한 작업을 자동 재시도시키지 않는다.

### 2. 권장: 구간별 음성 추출과 순차 인식

초기 실험값으로 10~20분 구간을 제안한다. 20분 음성은 약 36.6MiB다. 전체 WAV를 만든 뒤 나누는 방식보다 원본에서 필요한 구간을 추출하고 처리 후 지우면 임시 음성 디스크 사용량도 줄일 수 있다. 원본 다운로드 용량은 별도로 남는다. 최적 구간 길이는 대표 음성 실험으로 결정해야 한다.

FFmpeg는 시간 기반 분할을 지원한다. 분할 경계가 프레임 경계에 따라 달라질 수 있으므로 요청한 간격만 믿지 말고 실제 구간 시작 시각이나 표본 위치를 기록해야 한다. [FFmpeg 공식 분할 문서](https://ffmpeg.org/ffmpeg-formats.html#segment_002c-stream_005fsegment_002c-ssegment)

필수 동작:

- 각 구간의 인식 시간을 원본 시간으로 보정하고 SRT (영문 원문: SubRip Subtitle: 번호와 시간 구간이 있는 자막 형식) 번호를 다시 부여한다.
- 문장 중간 절단, 경계 음성 누락, 중복 자막을 비교한다. 겹치는 구간을 쓰면 중복 제거도 함께 설계한다.
- 실패 구간과 완료 구간을 기록하여 중간 실패 후 전체 인식을 반복하지 않게 한다.
- 모든 구간이 성공하고 시간 순서·범위를 검증한 뒤에만 최종 완료 처리한다.
- 구간 종료마다 임시 음성을 지우고 취소·재시작 시 남은 파일과 진행 기록을 정리한다.

가장 싼 실험은 문장이 경계에 걸린 2~3구간의 음성으로 전체 인식과 분할 인식을 비교하는 것이다. 자막 시간 오차·누락·중복 기준을 먼저 정하고 기준을 만족하지 못하면 구간 길이·겹침 방식을 조정한다. 짧은 실험을 통과한 뒤 이번 길이의 원본을 실제 worker에서 검증한다. 적용 시 기존 단일 파일 경로를 유지해 짧은 입력의 회귀와 롤백을 쉽게 한다.

현재 자막 함수가 `main.ts`에 닫혀 있어 외부 저장소 없이 정식 회귀 테스트를 붙이기 어렵다. 진단 도구의 소스 추출은 임시 해결책이며 장기 구현에서는 자막 처리 진입점에 외부 의존성을 주입할 수 있는 경계를 마련하는 편이 적합하다.

### 3. 사전 안내와 실패 상세 개선

지금은 전체 원본을 내려받고 WAV를 다 만든 뒤 한도를 검사한다. 변환 전에 ffprobe로 음성 길이를 읽어 예상 크기를 계산하면 불필요한 전체 변환을 줄일 수 있다. 브라우저 길이 검사는 빠른 안내용이며 worker 검증을 대체하지 않는다. 메타데이터 누락·손상에 대비해 실제 출력 바이트 제한도 유지한다.

사용자에게 실제 크기, 한도, 다음 행동을 안전한 값으로 안내하는 것이 좋다. 현재 화면의 “요청 설정으로 돌아가기”는 크기 제한을 바꿀 수 없는 모델 선택만으로는 문제를 해결하지 못한다. 분할 기능 전에는 짧은 구간 파일로 재시도하는 안내가 필요하다.

### 함께 검토해야 할 운영 경계

현재 worker는 다운로드와 자막을 한 건씩 처리한다. 한도를 올리거나 구간을 순차 처리해도 긴 작업이 다른 작업의 대기시간을 늘릴 수 있다. 구간 분할 자체가 작업 간 공정한 스케줄링을 제공하지는 않는다.

`WORKER_PROCESSING_TIMEOUT_MS=3600000`은 child process를 1시간 뒤 강제 종료하는 타이머가 아니다. `restoreStuckJobs`가 오래된 작업을 대기로 되돌리는 기준이며 현재 단일 루프는 작업 완료를 기다린다. 다중 worker 또는 재시작 시 살아 있는 장기 작업이 재접수될 가능성을 막으려면 작업별 소유권·생존 갱신과 조건부 완료 처리를 검토해야 한다. 이번 실패 원인으로 확인된 문제는 아니며 긴 작업 지원의 설계 검토 사항이다.

입력 파일을 MP3로 단순 교체하는 방안은 현재 WAV 재변환과 사전 크기 검사를 유지하면 효과가 없다. 최신 whisper.cpp의 입력 형식 지원은 실행 빌드에 따라 확인해야 한다. 공식 저장소 개요는 WAV 변환 예제를 제공하지만 CLI 문서는 복수 형식 지원을 표시하므로 운영 바이너리의 기능을 확인하지 않은 압축 입력 전환은 권장하지 않는다. [whisper.cpp 개요](https://github.com/ggml-org/whisper.cpp), [CLI 공식 문서](https://github.com/ggml-org/whisper.cpp/blob/master/examples/cli/README.md)

## 검증 범위와 남은 일

- 확인: 해당 작업의 실제 저장 기록, 현재 코드·설정·문서, 동일 오류 반복 재현, 한도 경계와 한도 상향 대조, 실제 로컬 FFmpeg 변환 형식.
- 미확인: 실패 당시 실행 worker의 환경·바이너리·프로세스 로그, 원본의 실제 재생시간, 원본 전체 Whisper 인식, 메모리·처리시간, 분할 자막 품질.
- 제품 수정·배포·작업 재시도는 수행하지 않았다. 요청 범위가 조사이므로 스킬의 수정·완치 검증 단계는 적용하지 않았다. 당시 재현 도구는 해당 증상에서 의도적으로 실패하도록 구성했다.
- 제품 코드에 계측을 추가하지 않았다. 2026-09-11 사용자 승인으로 임시 진단 도구와 원시 산출물을 삭제하고 이 분석 기록을 보존했다. 재현하려면 도구를 다시 준비해야 한다.
- 후속 전체 영상 실험 결과는 [실제 영상 검증 기록](real-video-test.md)에 정리했다. 위 미확인 항목은 최초 조사 시점 기준이다.
