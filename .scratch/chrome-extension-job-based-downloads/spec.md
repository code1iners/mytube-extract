# Chrome 확장 프로그램 job 기반 다운로드 전환

## Problem Statement

Web 앱과 API는 이미 `POST /downloads` → 상태 조회 → 완료 파일 다운로드로 이어지는 job 기반 흐름을 지원하지만, Chrome 확장 프로그램(팝업과 YouTube 오버레이 썸네일 버튼)은 여전히 호환용 `/audio`, `/video` 직접 다운로드 API를 사용한다.

이 때문에 사용자는 다음을 겪는다:

- 추출 처리가 즉시 끝나지 않을 때(예: 새 영상, 캐시되지 않은 화질) 확장 프로그램은 진행 상황을 전혀 보여주지 못한다. 브라우저의 단일 HTTP 다운로드가 조용히 오래 걸릴 뿐이다.
- 팝업을 닫으면 방금 보낸 요청이 어떻게 됐는지 알 방법이 없다. 오버레이로 요청한 경우는 애초에 팝업조차 열리지 않는다.
- 요청이 실패해도(예: 인증 필요, 지원하지 않는 포맷) 조용히 끊긴 다운로드로만 나타나고, 다시 시도하려면 처음부터 입력을 다시 해야 한다.
- 여러 영상을 연달아 요청하면(오버레이에서 특히 흔함) 먼저 보낸 요청의 진행 상황을 더 이상 확인할 수 없다.

## Solution

Chrome 확장 프로그램의 팝업과 오버레이 다운로드 요청을 모두 job 기반 흐름(`POST /downloads` → polling → `GET /downloads/:jobId/file`)으로 전환한다.

진행 상태 추적은 팝업이 아니라 **background service worker가 전담**해서, 팝업을 닫아도 요청이 이어지고, 여러 요청을 동시에 추적할 수 있으며, 완료·실패 시 데스크톱 알림을 받는다. 완료되면 사용자 개입 없이 자동으로 로컬 다운로드가 시작되고, 실패하면 알림에서 바로 재시도할 수 있다. 팝업을 열면 최근 요청 목록(최대 5건, 진행 중인 요청은 보호)을 확인할 수 있다.

기존 `/audio`, `/video` 직접 다운로드 API와 서버 쪽 `POST /downloads` 계약은 변경하지 않는다. 파일명 커스터마이징은 서버 요청 없이 클라이언트가 로컬 저장 시점에 지정하는 방식으로 유지한다.

## User Stories

1. As a 확장 프로그램 팝업 사용자, I want 추출 요청을 job으로 제출하고 그 결과를 job 상태로 추적하고 싶다, so that 요청이 대기/처리/완료 중 어느 단계인지 알 수 있다.
2. As a YouTube 페이지의 오버레이(썸네일 버튼) 사용자, I want 클릭 한 번으로 요청을 job으로 제출하고 싶다, so that 팝업을 열지 않고도 지금처럼 바로 추출을 시작할 수 있다.
3. As a 확장 프로그램 사용자, I want 팝업을 닫은 뒤에도 방금 보낸 요청이 계속 추적되기를 원한다, so that 처리 중에 팝업을 닫아도 요청을 잃지 않는다.
4. As a 확장 프로그램 사용자, I want 요청이 완료되면 자동으로 로컬 다운로드가 시작되기를 원한다, so that 지금과 동일하게 별도로 다운로드 버튼을 누를 필요가 없다.
5. As a 확장 프로그램 사용자, I want 요청이 완료되거나 실패하면 데스크톱 알림을 받고 싶다, so that 팝업을 다시 열어 확인하지 않아도 결과를 알 수 있다.
6. As a 확장 프로그램 사용자, I want 실패 알림에서 바로 재시도할 수 있기를 원한다, so that 팝업을 열어 입력을 다시 채우지 않아도 된다.
7. As a 팝업 사용자, I want 팝업을 다시 열었을 때 진행 중이거나 최근 완료/실패한 요청 목록을 보고 싶다, so that 이전에 무엇을 요청했는지 놓치지 않는다.
8. As a 팝업 사용자, I want 새 요청 폼이 항상 화면에 보이기를 원한다, so that 이전 요청 목록을 확인하면서도 바로 다음 요청을 넣을 수 있다.
9. As a 팝업 사용자, I want 여러 영상을 연달아 요청해도 각각의 진행 상황을 따로 확인하고 싶다, so that 나중에 보낸 요청이 먼저 보낸 요청의 상태를 덮어쓰지 않는다.
10. As a 확장 프로그램 사용자, I want 오래된 완료·실패 요청이 목록에서 자동으로 정리되기를 원한다, so that 목록을 직접 청소할 필요가 없다.
11. As a 확장 프로그램 사용자, I want 진행 중인 요청은 목록이 꽉 차도 자동으로 지워지지 않기를 원한다, so that 아직 끝나지 않은 요청의 상태를 잃지 않는다.
12. As a 팝업 사용자, I want 저장할 파일명을 직접 입력할 수 있기를 원한다, so that 지금처럼 원하는 이름으로 파일을 저장할 수 있다.
13. As a 오버레이 사용자, I want 영상 제목 기반으로 자동으로 정리된 파일명이 사용되기를 원한다, so that 지금과 동일한 동작을 유지할 수 있다.
14. As a 확장 프로그램 사용자, I want 동일한 영상·형식·화질을 이미 처리해 둔 asset이 있으면 즉시 완료 처리되기를 원한다, so that 중복 처리를 기다리지 않는다(서버가 이미 지원하는 동작을 그대로 이어받는다).
15. As a 확장 프로그램 사용자, I want 요청 직후에는 짧은 간격으로 상태가 빠르게 갱신되기를 원한다, so that 대부분의 짧은 요청에서 체감 대기 시간이 거의 없다.
16. As a 확장 프로그램 사용자, I want background service worker가 중간에 종료되더라도 진행 중인 요청 추적이 끊기지 않기를 원한다, so that 브라우저가 알아서 service worker를 재우거나 깨워도 결과를 놓치지 않는다.
17. As a 개발자, I want 팝업이 열려 있는 동안에도 background 하나만 실제 상태를 조회하기를 원한다, so that 팝업과 background가 각각 따로 서버에 중복 요청을 보내지 않는다.
18. As a 팝업 사용자, I want 팝업이 열려 있는 동안 상태 변화가 실시간으로 화면에 반영되기를 원한다, so that 수동으로 새로고침하지 않아도 최신 상태를 본다.
19. As a 오버레이 사용자, I want 클릭 직후 "요청을 시작했습니다" 같은 접수 확인만 페이지 안에서 보고 싶다, so that 이후 진행 상황은 알림과 팝업 목록에서 확인하면 되고 페이지가 복잡해지지 않는다.
20. As a 확장 프로그램 사용자, I want 서버가 거부한 요청(잘못된 URL, 지원하지 않는 포맷 등)에 대해 명확한 오류 메시지를 받고 싶다, so that 무엇이 잘못됐는지 알 수 있다.
21. As a 확장 프로그램 사용자, I want 오디오/비디오 화질 선택지가 서버가 실제로 지원하는 값으로 제한되기를 원한다, so that 존재하지 않는 화질을 요청해서 거부당하는 일이 없다.
22. As a 외부 도구를 통해 `/audio`, `/video`를 직접 호출하는 사용자, I want 기존 직접 다운로드 API가 계속 동작하기를 원한다, so that 이번 전환이 외부 호환성을 깨지 않는다.
23. As a 확장 프로그램 사용자, I want 브라우저를 완전히 재시작해도 아직 끝나지 않은 요청이 있으면 다시 추적되기를 원한다, so that 재시작 타이밍 때문에 요청을 잃지 않는다.
24. As a 개발자, I want job 추적/알림/자동 다운로드 로직이 실제 Chrome API 없이도 검증 가능하기를 원한다, so that 빠르고 안정적인 자동 테스트를 유지할 수 있다.

## Implementation Decisions

- **추적 주체**: 진행 상태 추적, polling, 알림, 자동 다운로드는 모두 background service worker가 전담한다. 팝업은 상태를 직접 조회하지 않고, 저장된 상태 변경을 구독해서 화면만 갱신한다(단일 polling 주체).
- **폴링 전략**: job 생성 직후에는 service worker가 자연히 활성 상태로 유지되는 동안 짧은 간격으로 상태를 확인하는 "빠른 경로"를 쓴다. service worker가 중간에 종료되는 경우를 대비해 상태를 영속 저장소에 남겨두고, 배포판 기준 최소 주기가 1분인 반복 알람으로 상태 확인을 재개하는 "복구 경로"를 함께 둔다. 브라우저 재시작 후에도 아직 끝나지 않은(대기/처리 중) 요청은 저장된 상태를 읽어 추적을 재개한다.
- **범위**: 팝업 제출과 오버레이(썸네일 버튼) 제출을 모두 이번 전환에 포함한다. 두 진입점 모두 같은 background 추적 로직을 공유한다.
- **오버레이 표시**: 오버레이 쪽 페이지 내 알림(toast)은 요청 접수 확인 한 번만 표시한다. 진행률을 페이지 안에서 실시간으로 갱신하는 별도 UI는 만들지 않는다. 이후 진행 상황은 알림과 팝업 목록이 담당한다.
- **다중 job 추적**: background는 동시에 여러 job을 개별적으로 추적한다. 각 job은 독립적인 상태(대기/처리 중/완료/실패)를 갖는다.
- **목록 보관 정책**: 최근 job은 최대 5건까지 유지한다. 6번째 job이 추가되면 완료되거나 실패한 job 중 가장 오래된 것부터 제거한다. 아직 대기 중이거나 처리 중인 job은 목록이 가득 차도 자동으로 제거하지 않는다.
- **팝업 레이아웃**: 팝업은 항상 새 요청 폼을 보여주고, 그 아래에 스크롤 가능한 최근 요청 목록을 함께 보여준다. 요청 제출이 화면 전체를 다른 화면으로 바꾸지 않는다.
- **자동 다운로드**: job이 완료 상태가 되면 사용자 조작 없이 즉시 로컬 다운로드를 시작한다. 목록에 별도의 "다운로드" 버튼은 없다.
- **알림**: 완료·실패 시 데스크톱 알림을 보낸다. 실패 알림에는 동일한 파라미터로 새 job을 다시 생성하는 재시도 동작을 연결한다.
- **파일명**: 서버 쪽 job 생성 요청에는 파일명을 보내지 않는다(서버는 지금처럼 영상 제목 기반으로 저장 파일명을 정한다). 대신 완료된 job의 파일을 로컬에 저장하는 시점에, 클라이언트가 가지고 있는 사용자 지정 파일명(팝업 입력값) 또는 영상 제목 기반 자동 생성 파일명(오버레이, 기존 로직 재사용)을 저장 파일명으로 지정한다. 기존 파일명 정리(경로 구분자·제어 문자 제거) 규칙을 그대로 재사용한다.
- **화질 입력 값 제한**: job 생성 요청은 서버가 지원하는 고정된 화질 값(오디오 128/192/320, 비디오 360/720/1080)만 허용한다. 지금 팝업의 자유 입력(임의 숫자) 필드는 이 고정 값 중에서 고르는 선택형 입력으로 바뀐다. Web 앱이 이미 쓰고 있는 화질 선택지 구성을 그대로 따른다.
- **호환성**: 기존 `/audio`, `/video` 직접 다운로드 API와 그 파일명 옵션은 외부 호환용으로 그대로 유지한다. 서버 쪽 `POST /downloads` 계약(요청·응답 스키마)은 변경하지 않는다.
- **핵심 모듈(신규)**: job 생성, 상태 저장·조회, 폴링 스케줄링, 완료/실패 시 부수효과(자동 다운로드 호출, 알림 발송, 목록 상한 적용)를 한데 모으는 job 관리 모듈을 background에 새로 둔다. 이 모듈은 API 클라이언트, 저장소, 다운로드 실행, 알림 발송, 폴링 스케줄링을 각각 별도 의존성으로 주입받는 형태로 만들어서, 실제 Chrome API나 네트워크 없이도 독립적으로 검증할 수 있게 한다.
- **기존 모듈 확장**: 팝업의 요청 모델은 그대로 유지하되, 제출 시 직접 다운로드를 호출하는 대신 job 생성을 요청하고, 화면에 보여줄 상태를 단일 상태 대신 job 목록으로 바꾼다. 오버레이의 background 처리 로직도 직접 다운로드 호출 대신 같은 job 관리 모듈을 호출하도록 바꾼다.
- **필요 권한 추가**: 알림 발송을 위한 브라우저 권한이 매니페스트에 추가로 필요하다.

## Testing Decisions

- 좋은 테스트란 실제 Chrome API·네트워크 없이, 의존성을 가짜(fake)로 주입한 상태에서 "입력 상태 → 어떤 부수효과가 호출됐는지 / 최종 상태가 무엇인지"라는 관찰 가능한 동작만 검증하는 테스트다. 내부 함수 구현이 아니라 모듈이 외부에 노출하는 동작을 검증한다.
- **핵심 검증 대상**: 새로 만드는 job 관리 모듈. API 클라이언트, 저장소, 다운로드 실행, 알림 발송, 폴링 스케줄링을 각각 가짜로 주입해서, 대기→처리 중→완료 전환, 완료 시 자동 다운로드 호출, 실패 시 알림+재시도 연결, 목록 상한 적용(진행 중 job 보호 포함), service worker 재시작 후 재개 시나리오를 검증한다. 폴링 스케줄링은 실제 타이머 대신 수동으로 진행시킬 수 있는 가짜를 주입해서 시간 경과를 테스트 안에서 결정적으로 재현한다.
- **확장 검증 대상**: 팝업의 요청 모델. 제출 시 직접 다운로드 대신 job 생성 요청을 보내는지, 여러 job 상태 변화가 목록 형태의 화면 상태로 올바르게 반영되는지 검증한다. 기존 `tests/integration/popup-download-model.test.ts`의 가짜 의존성 주입 패턴을 그대로 확장한다.
- **얇은 어댑터 검증**: 새로 추가하는 저장소·알림 어댑터는 기존 `downloads-adapter`, `storage-adapter` 테스트와 같은 방식으로, 가짜 Chrome 전역 객체를 대상으로 최소한의 위임 동작만 검증한다.
- **background wiring은 별도 단위 테스트 대상이 아니다**: 지금도 `background.ts`처럼 메시지를 받아 모델을 호출하는 얇은 연결 코드는 별도 테스트 파일 없이 얇게 유지하는 것이 기존 관례다. 이번에도 동일하게 따른다.
- **브라우저 smoke 테스트**: 기존 `tests/browser/popup-smoke.mjs`(실제 빌드 결과물로 팝업을 띄우는 Playwright 기반 smoke test)를 확장해서, 새 요청 폼과 최근 요청 목록이 정상적으로 렌더링되는지 정도의 최소 스모크 수준으로만 확인한다. job 상태 전이 로직 자체는 위 job 관리 모듈 테스트가 담당한다.

## Out of Scope

- 서버(`apps/api`, `apps/worker`)의 `POST /downloads` 계약, 화질 값 목록, 파일명 생성 정책 변경. (`docs/unimplemented/current-unimplemented.md`의 "Web 앱 파일명 입력" 항목과는 분리된 범위다.)
- 계정 기반 서버 요청 이력이나 기기 간 동기화.
- job 진행률을 대기/처리 중/완료 3단계보다 세밀하게 보여주는 것(서버가 아직 세밀한 진행률을 제공하지 않는다).
- job 취소 기능(서버에 취소 API가 없다).
- 고정 extension ID 기반 CORS 허용, Chrome Web Store 배포 관련 작업.
- 오버레이 페이지 내 실시간 진행률 UI.

## Further Notes

- 화질 입력을 자유 숫자 입력에서 고정 선택지로 바꾸는 결정은 이번 대화에서 명시적으로 확인받은 사항이 아니라, `POST /downloads`가 고정된 화질 값만 허용한다는 기존 서버 계약과의 충돌을 피하기 위해 spec 작성 중 발견하고 내린 판단이다. 구현 전에 이 부분만 별도로 한 번 더 확인하는 것을 권장한다.
- 이 작업은 원래 "팝업의 제출 로직만 job polling으로 바꾸는" 좁은 범위로 제안됐으나, 논의 과정에서 background 상태 관리·다중 job 목록·알림·팝업 UI 재설계·오버레이 통합까지 포함하는 것으로 범위가 넓어졌다. 실제 구현 시 여러 PR/커밋으로 나누는 것을 고려할 만하다.
- background 영속 추적 + 하이브리드 폴링(빠른 경로 + 알람 기반 복구 경로) 조합은 되돌리기 어렵고 트레이드오프가 있는 아키텍처 결정이라 ADR 후보로 남겨뒀다(그릴링 세션에서 제안, 아직 작성 여부는 확정하지 않음).
