# nGKd4yTP3M8 1080p VIDEO_TOO_LARGE 진단

2026-09-13. 요청 범위는 재현과 개선 방향 수립이다. 제품 소스·설정 변경, 배포, 전체 미디어 다운로드는 하지 않았다.

## 재현 증거

공개 서비스 `POST https://mytube-extract-api.codeliners.cc/downloads`에 다음 요청을 한 번 보냈다.

```json
{"type":"video","url":"https://youtu.be/nGKd4yTP3M8","quality":"1080"}
```

작업 `dc2d9e4a-21ad-4dcd-98b8-a660843cece8`이 queued에서 failed로 전환됐다. 조회 응답은 `errorCode: VIDEO_TOO_LARGE`, `quality: 1080`, `downloadUrl: null`이며 안내는 “파일 크기가 커서 현재 설정으로 처리할 수 없습니다. 낮은 화질로 다시 시도해 주세요.”였다. 사용자가 적은 VIDOE_TOO_LARGE의 실제 코드 표기는 VIDEO_TOO_LARGE다. 운영에 진단용 실패 요청 한 건이 남는다.

로컬 yt-dlp 2026.08.19, Node v24.18.0으로 worker와 같은 selector 및 `--js-runtimes node --no-playlist --dump-single-json`을 사용해 실제 메타데이터를 받았다. 원본 응답은 메모리에서만 다루고 서명 URL·헤더·쿠키가 없는 수치 허용 목록을 `metadata.json`에 보존했다. 운영 worker의 버전과 원본 메타데이터는 직접 조회하지 않았다.

```sh
pnpm --filter worker run build
node .scratch/video-too-large-diagnosis/repro.cjs
```

현재 소스로 빌드한 실제 `runVideoPreflight`에 캡처 응답을 재생한다. 네트워크만 대체한다. 두 번 연속 1초 미만, 종료 코드 1:

```text
FAIL: VIDEO_TOO_LARGE selected video is too large: 1186289151 bytes
```

성공하면 종료 코드 0, 다른 오류는 2다. 최소 입력은 `requested_formats: [{filesize:895583878},{filesize:290705273}]`이며 둘 중 하나를 제거하면 실제 사전 검사가 통과한다.

## 원인과 가설 검증

현재 worker는 `apps/worker/src/worker.logic.ts`의 `MAX_VIDEO_ESTIMATED_BYTES = 1024 * 1024 * 1024`를 적용한다. `createVideoPreflightDecision`은 선택된 영상·음성 각각의 `filesize`를 우선하고 없으면 `filesize_approx`를 합한다. `video-preflight.ts`는 기본 제한을 그대로 사용한다. 현재 환경 변수로 변경할 수 없다.

실제 메타데이터 기준 길이는 19,864초, 약 5시간 31분이다. 기본 선택은 AV1 1080p60 영상 399와 Opus 음성 251이다.

| 항목 | 바이트 |
|---|---:|
| 영상 399 | 895,583,878 |
| 음성 251 | 290,705,273 |
| 합계 | 1,186,289,151 |
| 제한 1GiB | 1,073,741,824 |
| 초과 | 112,547,327 |

GiB는 1,073,741,824바이트다. 이 크기는 제공자가 반환한 파일 크기이며 실제 다운로드 후 측정한 최종 병합 파일 크기는 아니다.

가설은 제한 초과, 더 작은 동급 포맷 선택 가능성, 추정 오차 순서로 공개한 뒤 비교했다.

```sh
node .scratch/video-too-large-diagnosis/probe.cjs
```

| 단일 변수 비교 | 결과 |
|---|---|
| 기본 399+251, 1GiB | VIDEO_TOO_LARGE |
| 같은 입력, 1.25GiB | 통과 |
| 같은 입력, 1.5GiB | 통과 |
| 1080p 영상 유지, 음성만 250으로 변경 | 1,056,417,666바이트, 통과 |
| 음성 유지, 720p 영상 398로 변경 | 770,128,578바이트, 통과 |
| 정확한 크기 제거, 추정값만 사용 | 1,186,284,848바이트, 동일 실패 |

주원인은 고정 합산 크기 제한이다. 추정 오차는 4,303바이트로 이번 실패를 설명하지 않는다. 1080p 다른 영상 코덱 299/303은 영상만으로도 1GiB를 넘으므로 코덱 변경만으로 해결되지 않는다. 음성 250은 약 64.8kbps이며 기본 251은 약 117.1kbps다. 음성 변경은 품질 변경을 수반하고 한도 여유가 17,324,158바이트뿐이다.

현재 processor는 사전 검사 → 제목 조회 → 다운로드 → 업로드 순서다. 이번 경로는 다운로드·저장소 업로드 전에 거부된다. API의 안내 메시지는 제한과 합산 크기를 보여 주지 않는다.

## 권장 개선 방향

1. **우선: worker의 영상 제한을 환경 변수로 설정 가능하게 한다.** 예를 들어 `VIDEO_MAX_ESTIMATED_BYTES`를 새로 정의하고 미설정 기본값은 기존 1GiB를 유지한다. 양의 안전한 정수 검증과 example/운영 문서가 필요하다. 이 영상의 품질을 유지하려면 1.25GiB만으로도 사전 검사는 통과한다. 운영 후보는 여유를 둔 1.5GiB이며 전체 처리 자원 측정 후 확정한다. 자막용 `SUBTITLE_AUDIO_MAX_BYTES` 또는 업로드 한도 변경은 이 오류에 영향을 주지 않는다.
2. **큰 작업의 보호 경계를 같이 확인한다.** 사전 메타데이터와 실제 다운로드는 독립 요청이므로 선택 포맷이 달라질 수 있다. 사전 검사 결과의 포맷 고정 또는 재검증, 실제 출력 크기 검사, 임시 디스크 여유, 실행 제한을 검토한다. 출력 크기 검사만으로 다운로드 중 디스크 고갈을 막을 수는 없다. 현재 업로드는 파일 스트림과 multipart를 사용하지만 전체 작업의 자원 안전성을 증명하지 않는다.
3. **오류 안내에 선택 크기와 허용 크기를 제공한다.** 서버에서 구조화된 안전한 수치를 전달하고 화면에 제한과 가능한 다음 행동을 표시한다. 스택·서명 URL을 응답에 넣지 않는다. 1080p 요청을 자동으로 720p나 낮은 음질로 바꾸는 것은 별도 제품 결정으로 둔다.

음질을 낮춰 기존 제한에 맞추는 선택지도 있지만 이번에는 여유가 작고 요청의 음질 의미가 바뀌므로 우선안으로 삼지 않는다. 같은 1080p 재요청만으로는 현재 제한이 바뀌지 않는다.

## 가장 싼 후속 검증과 중단·복구

- 먼저 현재 캡처를 사용해 기본 제한, 설정 제한, 경계값 동일/1바이트 초과, 잘못된 설정값을 검증한다. 기존 `video-preflight.spec.ts`와 worker processor 경계가 회귀 테스트 후보다.
- 그다음 운영과 분리된 worker에서 이 영상 한 건을 원래 1080p+음성 품질로 다운로드·병합한다. 병합 전후 임시 파일이 함께 존재할 수 있어 입력과 출력 합계 약 2.37GB 외 추가 여유를 확보하고 실제 최대 디스크·메모리·시간을 측정한다. 이 값은 산술 계획치이며 실측치가 아니다.
- 자원 예산 초과, 제한 시간 초과, 메타데이터와 다운로드 포맷 불일치가 발생하면 중단하고 임시 파일을 정리한다. 자원 여유가 확인되기 전 운영 제한을 올리지 않는다.
- 마지막으로 새 queued 요청에서 저장소 업로드, 완료 상태, 다운로드 응답, 실제 1080p·소리 재생까지 검증한다. 캐시 재사용 성공과 새 추출 성공을 구분한다.
- 운영 반영 후 문제가 있으면 기존 1GiB 설정/이전 worker로 복원한다. 이미 실패한 요청은 자동 재실행되지 않으므로 새 요청이 필요하다.

## 검증 범위와 산출물

확인: 공개 서비스 동일 오류, 실제 제공자 메타데이터, 현재 worker 빌드 성공, 실제 사전 검사 반복 실패 및 비교 실험. 미확인: 제한 상향 후 전체 다운로드·병합·업로드·재생, 운영 worker 자원과 버전. 로컬 API와 Docker daemon은 실행되지 않았다.

진단 도구와 민감 필드 제거 메타데이터는 이 디렉터리에 보존했다. 제품 코드 계측은 추가하지 않았다. 기존 다른 작업의 변경사항과 `.scratch/audio-too-large-diagnosis/`는 수정하지 않았다. 요청 범위에 따라 스킬의 수정·회귀 통과 단계는 후속 구현으로 남긴다.
