# 요청 내역의 요청 영상 제목 표시

Status: ready-for-agent

## 문제 정의

Web 앱의 요청 내역은 영상 요청을 고정된 종류 이름으로 표시하여 어떤 YouTube 영상을 요청했는지 구분하기 어렵다. 같은 형식과 품질로 여러 영상을 요청하면 시각 정보만으로 원하는 요청을 찾기 어렵다.

원본 제목은 현재 추출 결과물에만 저장된다. 상태 응답에는 제목이 없으며, 추출에 실패하거나 결과물이 만료되어 정리되면 제목을 활용할 수 없다. 완료된 파일의 이름을 보여주는 것만으로는 처리 중·실패·만료 내역의 식별 문제를 해결할 수 없다.

## 해결 방향

영상·오디오 추출 요청에서 처음 확보한 **요청 영상 제목**을 내역 항목의 주 제목으로 표시한다. 비디오·오디오 구분, 품질, 요청 시각은 보조 정보로 유지한다.

기존 추출 처리에서 제목을 얻는 즉시 요청에 보존하고 상태 조회에 반영한다. 제목은 이후 원본 제목이 바뀌거나 추출이 실패하거나 결과물이 만료·정리되어도 유지한다. 아직 제목을 확보하지 못했거나 조회에 실패한 경우에는 원본 영상 링크로 요청을 식별하게 한다.

기존 내역은 서버에 남아 있는 제목을 활용한다. 없어진 과거 제목을 외부에서 재조회하지 않는다. 접수 시 별도 제목 조회도 추가하지 않는다.

## 사용자 이야기

1. Web 앱 사용자로서, 요청 내역에서 영상 제목을 보고 싶다. 어떤 영상을 요청했는지 바로 구분하기 위해서다.
2. 여러 영상을 요청한 사용자로서, 같은 품질의 요청들도 제목으로 구분하고 싶다. 원하는 결과를 정확히 찾기 위해서다.
3. 오디오 추출 사용자로서, 원본 영상의 제목을 보고 싶다. 어떤 영상에서 추출한 오디오인지 알기 위해서다.
4. 같은 영상의 비디오와 오디오를 요청한 사용자로서, 제목과 함께 추출 종류를 보고 싶다. 받을 파일을 구분하기 위해서다.
5. 여러 품질을 요청한 사용자로서, 제목 아래 품질과 요청 시각을 보고 싶다. 같은 영상의 요청을 구분하기 위해서다.
6. 처리 중인 요청을 확인하는 사용자로서, 제목을 확보했다면 완료 전에 보고 싶다. 기다리는 대상이 맞는지 확인하기 위해서다.
7. 대기 중인 요청을 확인하는 사용자로서, 제목이 없어도 원본 영상 링크를 보고 싶다. 요청 대상을 식별하기 위해서다.
8. 제목 조회에 실패한 사용자로서, 영상 추출은 계속 진행되기를 원한다. 보조 정보의 실패 때문에 파일을 받지 못하는 일을 피하기 위해서다.
9. 제목 확보 전에 추출이 실패한 사용자로서, 원본 링크를 확인하고 싶다. 어떤 영상에서 문제가 생겼는지 알기 위해서다.
10. 제목 확보 후 추출이 실패한 사용자로서, 확보한 제목이 남기를 원한다. 실패한 요청을 알아보기 위해서다.
11. 완료된 요청을 확인하는 사용자로서, 제목과 다운로드 동작을 함께 사용하고 싶다. 원하는 파일을 정확히 받기 위해서다.
12. 파일 보관 기간이 지난 사용자로서, 요청 제목은 계속 보고 싶다. 만료된 요청의 대상을 알기 위해서다.
13. 페이지를 새로고침한 사용자로서, 이전과 같은 제목을 보고 싶다. 내역의 식별 정보가 사라지지 않게 하기 위해서다.
14. 원본 영상 제목이 바뀐 뒤 방문한 사용자로서, 해당 요청에서 처음 확보한 제목을 보고 싶다. 과거 내역의 이름이 임의로 달라지지 않게 하기 위해서다.
15. 기존 요청을 가진 사용자로서, 서버에 남아 있는 제목도 표시되기를 원한다. 새로 요청하지 않고 기존 내역을 알아보기 위해서다.
16. 과거 제목이 없는 사용자로서, 원본 영상 링크로 내역을 구분하고 싶다. 제목 복구를 기다리지 않고 내역을 사용하기 위해서다.
17. 내역에서 요청을 삭제하고 되돌린 사용자로서, 같은 요청 제목이 다시 나타나기를 원한다. 삭제 전 요청을 정확히 복원하기 위해서다.
18. 좁은 화면을 사용하는 사용자로서, 긴 제목과 링크가 있어도 주요 동작을 사용할 수 있기를 원한다. 다운로드와 삭제를 가림 없이 수행하기 위해서다.
19. 키보드와 보조 기술을 사용하는 사용자로서, 요청 제목·원본 링크·상태를 구분해 탐색하고 싶다. 원하는 요청을 정확히 조작하기 위해서다.
20. 자막 추출 사용자로서, 기존 자막 내역이 그대로 작동하기를 원한다. 영상 제목 개선으로 기존 사용 흐름이 달라지지 않게 하기 위해서다.

## 구현 결정

### 제목의 소유와 보존

- 요청 영상 제목은 추출 요청이 보유하는 선택적 정보로 둔다. 결과물의 제목이나 다운로드 파일명과 구분한다.
- 추출 요청에 제목을 저장할 nullable 필드를 추가한다. 제목이 없거나 공백뿐인 결과는 미확보 상태로 취급한다.
- 처음 확보한 유효한 제목만 저장한다. 이미 제목이 있는 요청은 재처리·중복 실행·결과물 변경으로 덮어쓰지 않는다. 동시 실행에서도 이 규칙을 지키는 조건부 저장을 사용한다.
- 결과물의 만료·삭제 및 요청 상태 전환은 요청 제목을 지우지 않는다. 이 계약은 요청 기록이 존재하는 동안 적용되며 별도의 영구 요청 보존 정책을 신설하지 않는다.
- 현재 결과물 제목과 다운로드 파일명 생성 계약은 유지한다.

### 제목 확보와 기존 요청

- 기존 작업 처리기의 제목 조회 경로를 사용한다. 조회가 성공하면 실제 다운로드·업로드 완료를 기다리지 않고 요청 제목을 저장한다.
- 기존 사전 검증과 추출 순서를 제목의 조기 확보만을 위해 재배치하지 않는다. 제목 조회 전에 실패한 요청에는 제목이 없을 수 있다.
- 제목 조회 실패는 미확보로 처리하고 기존 추출을 계속한다. 이 규칙이 데이터베이스 쓰기 실패까지 무조건 무시하라는 뜻은 아니다. 저장 실패를 보존 성공으로 보고하지 않는다.
- 기존 결과물을 재사용해 즉시 완료하는 경로도 결과물에 제목이 있으면 새 요청에 복사한다. 이때 외부 제목 조회는 추가하지 않는다.
- 기존 요청은 연결된 결과물에 남은 유효한 제목을 요청으로 이관한다. 기존 요청 제목이 있으면 덮어쓰지 않으며, 결과물이 없거나 제목이 없으면 미확보로 유지한다.
- 이관은 외부 서비스 없이 현재 저장값만 사용하며 반복 실행해도 확보된 제목을 변경하지 않는다. 같은 결과물을 참조하는 각 요청에 독립적으로 제목을 보존한다.
- 배포 순서는 필드 추가, 기존 제목 이관, 새 제목 저장·응답·표시 활성화를 포함한다. 전환 중 결과물 정리로 제목이 유실되지 않도록 정리 작업과 이관의 순서를 통제하고, 구 버전 작업 처리기의 잔여 실행이 끝난 뒤 누락분도 이관한다.
- 문제가 생기면 화면·서버 코드를 되돌릴 수 있도록 추가 필드는 호환적으로 도입한다. 이미 보존한 제목을 롤백 목적으로 삭제하지 않는다.

### 서버 응답과 Web 표시

- 영상·오디오 요청의 접수 및 상태 조회 응답에 요청 영상 제목과 원본 영상 링크 정보를 추가한다. 제목은 문자열 또는 null로 표현하며 요청에 보존된 값을 기준으로 한다.
- 원본 링크는 서버에 저장된 요청의 YouTube 식별 정보에서 구성한다. 제목이 없더라도 서로 다른 영상을 구분할 수 있어야 한다.
- 제목 제공을 위해 접수·상태 조회·내역 열기에서 외부 제목 조회를 실행하지 않는다.
- 서버 응답 타입과 Web 응답 검증을 함께 갱신한다. 기존 상태·진행률·다운로드 주소·실패 메시지의 의미는 변경하지 않는다.
- 요청 내역은 유효한 제목이 있으면 이를 항목의 주 제목으로 표시한다. 없으면 영상 식별자가 보이는 원본 링크를 제공하며 모든 항목이 동일한 안내 문구로만 보이지 않게 한다.
- 비디오·오디오 구분, 품질, 요청 시각과 현재 상태는 보조 정보로 유지한다. 동일 영상의 여러 요청을 합치거나 정렬을 변경하지 않는다.
- 제목은 일반 텍스트로 렌더링한다. 긴 제목·공백 없는 문자열·긴 링크를 줄바꿈하여 좁은 화면에서도 항목과 동작이 넘치지 않게 한다.
- 기존 상태 조회 주기로 제목을 반영하며, 제목만을 위한 추가 주기적 조회나 종료된 요청의 반복 조회는 도입하지 않는다.
- 항목 제목의 접근 가능한 연결 관계, 삭제 뒤 포커스 이동, 되돌리기 뒤 제목 포커스를 유지한다. 제목 갱신을 반복 공지하지 않는다.
- 브라우저 접수증에는 기존 식별 정보만 저장한다. 제목과 원본 링크는 서버 응답을 사용하며 브라우저에 별도 제목 보관소를 만들지 않는다.
- 개인 사용 단계, 브라우저 중심 내역, 기존 YouTube 추출 경로의 재시도 정책을 유지한다.

## 테스트 결정

검증은 사용자가 관찰하는 제목·링크·상태·보존 결과를 기준으로 한다. 내부 함수 분할이나 호출 횟수 자체를 목표로 삼지 않는다. 다만 외부 재조회 금지는 외부 호출이 발생하면 실패하는 대역으로 검증한다.

### 기존 경계 재사용

- 기존 요청 내역 브라우저 검증을 주된 화면 경계로 확장한다. 실제 내역 화면에 제어된 상태 응답을 제공하여 제목 표시, 처리 중 제목 도착, 제목 없는 원본 링크, 비디오·오디오 구분, 새로고침, 긴 제목, 삭제·되돌리기 포커스를 확인한다.
- 기존 다운로드 서비스·응답 검증 테스트로 추가 응답 필드와 null 제목, 결과물 재사용, 실패·만료 상태의 제목을 검증한다. 기존 자막 내역과 다운로드 계약 회귀도 확인한다.
- 기존 작업 처리기 테스트는 제어 가능한 외부 추출 실행을 사용한다. 제목 조회 실패 이후에도 추출이 진행되는지 확인한다.

### 영속성 검증 보완

- 기존 서비스의 모의 데이터 테스트와 브라우저 응답 대역만으로는 제목 보존과 데이터 이관을 입증할 수 없다. 테스트가 소유하는 실제 로컬 데이터베이스 요청으로 저장·상태 조회·결과물 정리를 연결한 통합 검증을 추가한다.
- 작업 처리에 필요한 새 테스트 경계가 있으면 제목 저장 함수마다 나누지 않고, 외부 제목 조회·파일 처리를 제어할 수 있는 단일 요청 처리 진입점을 우선한다.
- 제목 확보 직후 다운로드를 일시 정지한 상태에서 서버 상태 응답을 읽어, 완료 전에 제목이 노출되는지 확인한다.
- 이후 추출 실패 및 결과물 만료·실제 정리 후 다시 상태를 조회하여 같은 제목이 남는지 확인한다. 단순 만료 시각 변경과 결과물 행 삭제를 구분한다.
- 제목 이관 전후로 제목이 있는 결과물, 제목 없는 결과물, 결과물이 없는 요청, 이미 요청 제목이 있는 경우, 여러 요청이 같은 결과물을 참조하는 경우를 검증한다.
- 이관 재실행과 중복 제목 저장 시도에서도 처음 저장한 제목이 유지되는지 검증한다. 과거 요청과 내역 조회에서 외부 제목 조회가 발생하지 않아야 한다.
- 검증 환경이 없거나 대상 데이터가 비어 있으면 통과로 처리하지 않는다. 테스트 소유 데이터를 생성·정리하고 실제 실행하지 못한 경계는 미검증으로 기록한다.

### 검증 결과의 범위

- 마지막 변경 이후 Web·서버·작업 처리기·데이터 모델에 해당하는 정적 검사와 자동 테스트를 실행한다. 작업 처리기 테스트가 빌드 결과를 실행하는 기존 방식임을 고려해 최신 빌드를 사용한다.
- 브라우저 검증에서는 좁은 화면과 확대 상태의 긴 제목, 키보드 링크 접근, 삭제·복원 포커스를 확인한다.
- 로컬 데이터베이스 통합 검증은 실제 YouTube·운영 작업 처리기·외부 파일 저장소의 성공 증거가 아니다. 기존 추출 동작을 바꾸지 않는 이번 범위에서는 실제 YouTube 추출을 자동 필수 검증으로 추가하지 않는다.
- 실제 외부 추출이나 보조 기술 확인을 수행했다면 별도로 기록하고, 대역 기반 검증 결과로 대신 주장하지 않는다.

## 범위 밖

- 자막 요청의 제목·파일명 표시 변경
- 요청 접수 즉시 별도 제목 조회, 제목을 위한 추가 재시도·주기적 조회
- 과거에 삭제되었거나 확보하지 못한 제목의 외부 재수집
- YouTube 최신 제목과 과거 요청 제목의 동기화
- 다운로드 파일명 정책 변경, 썸네일·채널명·재생시간 추가
- 제목 클릭으로 다운로드하는 동작, 요청 자동 재시도, 내역 묶기·검색·정렬 변경
- 계정, 다른 기기 동기화, 서버 요청 소유권 및 새로운 보존·삭제 정책
- Chrome 확장 프로그램의 화면 개선 및 운영 배포 실행

## 추가 메모

- 인터뷰의 Q1–Q5에 사용자가 모두 동의했으며, 스펙 생성 요청을 최종 범위 구체화의 근거로 삼는다.
- 구현 결정의 저장 필드·응답 확장·이관·검증 방식은 합의한 사용자 동작을 달성하기 위한 설계다. 제품 코드는 이 문서 작성 시점에 변경하지 않았다.
- 검증 경계는 기존 브라우저 테스트 중심과 로컬 데이터베이스 통합 보완으로 제안했다. 별도 응답이 없는 경우 이 기준을 적용하며 사용자가 추가로 승인했다고 표현하지 않는다.
- 현재 운영 계약을 설명하는 요청 내역 문서는 구현 시 실제 변경과 함께 갱신한다. 이 스펙 자체는 구현·검증 완료의 증거가 아니다.
